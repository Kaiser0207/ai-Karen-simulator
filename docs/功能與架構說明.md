## 二、目前已實作的功能

### 1. 多回合對話狀態機(核心)
用 **LangGraph** 把整場遊戲建模成一張狀態圖。一次 `graph.invoke` = 一個回合,跨回合的記憶由 checkpointer 自動保存。

### 2. 動態憤怒值系統
- 每回合 LLM(或 mock)評估玩家話術,回傳 `anger_change`(憤怒變化量)。
- 後端硬性夾限 `anger_change` 在 **±30**、憤怒值夾在 **0~100**(防暴衝、防玩家用話術作弊)。

### 3. 三種結局判定
- **成功(success)**:憤怒值 ≤ 0,或 LLM 判定玩家提出完美方案。
- **失敗(fail)**:憤怒值 ≥ 100(砸店/投訴)。
- **超時(timeout)**:回合數達上限仍未平息。
- 三種結局各有 scenario 預寫好的「結局台詞」,確保台詞與憤怒值一致。

### 4. 雙 LLM 角色
- **奧客大腦**:每回合扮演奧客 + 評估憤怒變化(結構化輸出 `CustomerTurn`)。
- **評審大腦**:遊戲結束後審視整場對話,輸出培訓報告(`JudgeReport`,含同理心/危機應變/法規遵從三維分數 + 話術建議)。

### 5. 結構化輸出
用 Pydantic schema 約束 LLM 回傳格式;真實模式下以 `with_structured_output()` 強制,格式錯會自動重試,後端不需手刻 JSON 解析。

### 6. 雙模式:mock / 真實 LLM 可切換
- **mock 模式**(`OKEKE_USE_MOCK=1`):用關鍵字規則模擬奧客,**免 API key**,適合測狀態機、省額度。
- **真實模式**(`OKEKE_USE_MOCK=0`):接 **Gemini 2.5-flash**,奧客回應自然、會翻舊帳、堅持訴求。
- 切換只改 `.env`,**節點層程式碼完全不動**(因為 LLM 呼叫封裝在 services 層)。

### 7. 多關卡(奧客圖鑑)
目前內建兩個角色:**張大媽(餐飲)**、**劉董(零售)**。新增角色只要加一個 JSON 檔,不用改程式。

### 8. 跨回合記憶與持久化
用 `SqliteSaver` 當 checkpointer,以 `thread_id` 為一場遊戲的識別,對話歷史與憤怒值自動保存(可持久化到 SQLite 檔)。

### 9. 設定集中管理(.env)
API key、供應商、模型名稱統一放 `.env`,由 `config.py` 載入;`.env` 已被 git 忽略,不會外洩。

## 三、檔案結構與每個程式的作用

```
final_project/
├── config.py              # 設定中心:從 .env 載入 key/供應商/模型名
├── run_demo.py            # Phase 1 驗證腳本(mock,跑三種結局)
├── smoke_test.py          # Phase 2 驗證腳本(真實 Gemini 跑一回合)
├── .env / .env.example    # 環境變數(實際 / 範本)
├── .gitignore             # 忽略 .env、.venv、*.db、logs/
├── pyproject.toml         # uv 專案設定與依賴
│
├── graph/                 # 【LangGraph 核心:遊戲邏輯】
│   ├── state.py           #   GameState:貫穿全場的共享狀態(憤怒值/回合/對話歷史…)
│   ├── schemas.py         #   CustomerTurn / JudgeReport:LLM 結構化輸出格式
│   ├── nodes.py           #   6 個節點函式(見下)
│   └── build.py           #   組裝狀態圖、串接節點與邊
│
├── services/              # 【外部服務轉接層】
│   └── llm.py             #   奧客大腦 + 評審;mock 與真實 LLM 兩套實作
│
├── scenarios/             # 【關卡內容】
│   ├── loader.py          #   載入關卡 JSON、組 system_prompt、建開局 state
│   ├── zhang_dama.json    #   角色:無理取鬧的張大媽(餐飲)
│   └── liu_dong.json      #   角色:攀關係要折扣的劉董(零售)
│
└── prompts/               # 【提示詞模板】
    ├── customer_system.txt#   奧客共用骨架(個性/情境/規則,角色變數待填)
    └── judge_system.txt   #   評審大腦的指示
```

### graph/state.py
定義 `GameState`(TypedDict)——所有節點共讀共寫的「筆記本」。欄位分四類:關卡靜態設定、動態狀態(憤怒值/回合/對話歷史)、本回合 I/O、結束相關。`messages` 用 `add_messages` reducer,新訊息會自動追加而非覆蓋。

### graph/schemas.py
兩個 Pydantic 模型:
- `CustomerTurn`:奧客每回合輸出(`reply` 台詞、`anger_change` ±30、`emotion` 情緒、`ended` 是否和解)。
- `JudgeReport`:結算報告(三維分數 + 好/壞話術 + 總評)。

### graph/nodes.py(6 個節點)
| 節點 | 作用 |
|------|------|
| `customer_brain` | 呼叫奧客 LLM,回傳台詞 + 憤怒變化 + 情緒,並把玩家與奧客的話追加進歷史 |
| `apply_state` | 夾限 `anger_change`、更新憤怒值(0~100)、回合 +1 |
| `classify_ending` | 判斷結局類型(fail/success/timeout/None)並寫進 state |
| `route_after_classify` | conditional edge:讀 state 決定「繼續」或「進入結局」 |
| `set_ending` | 附加 scenario 預寫的結局台詞、標記結束 |
| `judge` | 呼叫評審 LLM,產出報告 |

### graph/build.py
用 `StateGraph` 把節點與邊組起來,編譯成可執行的圖。流程:
```
START → customer_brain → apply_state → classify_ending ─┬─[continue]→ END
                                                        └─[ending]→ set_ending → judge → END
```

### services/llm.py
對外只暴露 `customer_turn(...)` 與 `judge_report(...)` 兩個函式,內部依 `OKEKE_USE_MOCK` 切換:
- **mock**:用關鍵字規則(同理 / 解決方案 / 官腔)計算憤怒變化,免 key。
- **真實**:`_get_chat()` 依 `LLM_PROVIDER` 建立 Gemini(或 Groq)模型,用 `with_structured_output` 取得型別安全輸出。

### scenarios/loader.py
- `list_scenarios()`:回傳關卡清單給下拉選單。
- `load(scenario_id)`:讀 JSON、用 `str.replace` 把角色變數填進 `customer_system.txt`、建立開局 state(含把開場白放進 `messages`)。

### config.py
用 `python-dotenv` 載入 `.env`,提供 `USE_MOCK`、`LLM_PROVIDER`、`GOOGLE_API_KEY`、`GROQ_API_KEY`、`CUSTOMER_MODEL`、`JUDGE_MODEL`。

## 五、如何啟動與操作

### 前置:安裝環境
```bash
cd final_project
uv sync                 # 依 pyproject.toml 建立 .venv 並安裝依賴
cp .env.example .env    # 第一次:複製範本,填入你的 API key
```
在 `.env` 設定:
- 要用真 LLM:`OKEKE_USE_MOCK=0`、`LLM_PROVIDER=gemini`、`GOOGLE_API_KEY=你的key`
- 只想測邏輯(免 key):`OKEKE_USE_MOCK=1`

### 啟動方式 A:mock 三結局驗證(免 key)
```bash
uv run python run_demo.py
```
**畫面會長這樣**(節錄成功場):
```
────────────────────────────────────────────────────────
🎬 示範一:成功平息(關卡:zhang_dama)
────────────────────────────────────────────────────────
😠 奧客:店長呢?叫你們店長出來!這什麼態度!菜裡有頭髮你們是要怎麼處理?
   憤怒值 50/100

🧑 店員:您好,我完全理解您的不滿,真的很不好意思讓您遇到這種狀況。
😠 奧客:聽起來你好像有在聽,那然後呢?
   憤怒值 38/100  (-12)  情緒=neutral  回合 1/8
   ...
   結局台詞:唉…算了,看你這麼有誠意,謝謝你願意聽我說,這樣處理我可以接受。
   >>> ⭐ 成功(和解) <<<

  📊 培訓報告
     同理心 67 / 危機應變 67 / 法規遵從 100
     ✅ 做得好:…   ❌ 可改進:…
```
會連續跑三場,分別觸發 **成功 / 失敗 / 超時**,用來驗證狀態機正確。

### 啟動方式 B:真實 Gemini 單回合測試
```bash
uv run python smoke_test.py
```
**畫面會長這樣**:
```
Provider=gemini  Model=gemini-2.5-flash  USE_MOCK=False
開場白: 店長呢?叫你們店長出來!…
店員: 真的很抱歉造成您的困擾,我馬上幫您這餐免單,並請廚房重做一份新的給您。
奧客: 免單是應該的啦！但你們以為這樣就沒事了嗎？…我要的是退一賠十！…
anger_change=-10  emotion=annoyed  ended=False

✅ Gemini 結構化輸出正常!
```

### 目前的操作流程(概念)
```
選關卡(載入角色 + 開場白)
   ↓
玩家輸入一句話(目前是程式內腳本 / 測試輸入)
   ↓
graph.invoke 跑一回合:奧客回應 + 憤怒值變化
   ↓
未結束 → 等下一句  |  已結束 → 播結局台詞 + 評審報告
```

> 註:目前是**指令列(CLI)/腳本**操作。**互動式輸入畫面與血條視覺化**會在 Phase 3(Gradio 網頁)實作——屆時操作會變成:網頁選關卡 → 打字/錄音 → 即時看聊天視窗與憤怒值進度條 → 結束看雷達圖。
