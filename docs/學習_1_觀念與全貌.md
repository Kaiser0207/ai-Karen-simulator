## 1. 一句話:這專案是什麼?

> 一個用 **AI 模擬奧客**、訓練「服務業危機溝通」的**回合制對話遊戲**。
> 玩家當店員,要在有限回合內把暴怒的 AI 奧客安撫下來;結束後 AI 教練給評分與建議。

它**不是**聊天機器人——它有血條(憤怒值)、有勝負(三種結局)、有評分。這是它和「一般 chatbot」最大的區別,答辯時要強調。

---

## 2. 核心比喻:回合制 Boss 戰

| RPG | 這個遊戲 |
|-----|---------|
| Boss 血條 | 憤怒值 0~100 |
| 你的攻擊 | 你講的話(話術) |
| 傷害數字 | `anger_change`(這句話讓憤怒 +/- 多少) |
| 回合上限 | 對話輪數(預設 8) |
| 打贏 / 打輸 | 和解 / 砸店 / 超時 |
| 結算畫面 | 評審報告(三維分數 + 建議) |

**差別**:你的「攻擊」是用講的,傷害由 AI 判斷。這就是全遊戲的靈魂。

---

## 3. 五個必懂的基礎觀念

這五個懂了,後面全部看得懂。

1. **LLM**:會「接話、生成文字」的 AI 模型(我們用 Google Gemini)。
2. **System Prompt**:偷偷給 LLM 的「角色設定卡」,玩家看不到。我們用它讓 LLM 扮演奧客。
3. **結構化輸出**:強迫 LLM 回**固定格式的資料**(台詞、憤怒變化、情緒、是否結束),而不是一段自由文字。
4. **狀態機(State Machine)**:有「目前狀態 + 變化規則」的系統。我們的狀態=憤怒值/回合/對話歷史。
5. **LangGraph**:把狀態機畫成「**節點(做事)+ 邊(決定下一步)**」的套件。整個遊戲就是一張這樣的圖。

> 還有一個之後會深入的:**記憶**——靠把「對話歷史」每回合重新餵給 LLM 來達成(第 4 課細講)。

---

## 4. 系統三層架構

```
玩家 → [前端] → [LangGraph 大腦] → [外部服務:LLM]
        (網頁/      (遊戲邏輯、       (Gemini 生成
         CLI)        狀態機、記憶)     台詞+評分)
```

- **前端**:玩家輸入、顯示(目前是 CLI;Phase 3 才做 Gradio 網頁)。
- **LangGraph 大腦**:本專題核心,管憤怒值、回合、結局判定。
- **外部服務**:真正會講話的 LLM。

設計重點:**LLM 的呼叫被封裝在「服務層」**,所以換模型、切 mock/真實,核心邏輯都不用改。

## 6. 一回合的資料流(高層預覽)

先有個印象,後面課會逐塊放大:

```
玩家講一句話
   ↓
customer_brain：呼叫 LLM → 得到(台詞 + 憤怒變化 + 情緒 + 是否和解)
   ↓
apply_state：更新憤怒值、回合 +1
   ↓
classify_ending：判斷結束了沒
   ↓
 ┌─ 沒結束 → 等玩家下一句
 └─ 結束了 → set_ending(結局台詞) → judge(評審報告)
```

## 🎓 老師可能問

**Q:你這個跟聊天機器人差在哪?**
A:聊天機器人是無狀態的一問一答;我們是有狀態的遊戲——有憤怒值血條、回合上限、三種勝負結局、結束有 AI 評分,核心是一台用 LangGraph 驅動的狀態機。

**Q:為什麼選 LangGraph?**
A:因為這遊戲本質是狀態機(狀態=憤怒值/回合,規則=怎麼變、何時結束)。LangGraph 天生用「節點+邊」表達狀態機,還自帶跨回合記憶,比手刻 if/else 清楚好維護。
