## 1. schemas.py —— LLM 的「輸出格式」

LLM 平常回一段自由文字,但我們需要它一次回**好幾個值**,所以用 Pydantic 模型規定格式。

### CustomerTurn:奧客每回合吐什麼

```python
Emotion = Literal["angry", "annoyed", "neutral", "calm", "happy"]

class CustomerTurn(BaseModel):
    reply: str                              # 奧客講的台詞
    anger_change: int = Field(ge=-30, le=30) # 這句話讓憤怒 +/- 多少
    ended: bool                             # 玩家是否提出完美方案、達成和解
    emotion: Emotion                        # 當下情緒(供前端換立繪/將來語音)
    concession_cost: int = Field(default=0, ge=0, le=100)  # 店員「這一句」讓掉的成本/原則彈性
```

逐欄位(共 5 個):
- **reply**:要顯示在聊天視窗的奧客台詞。
- **anger_change**:核心數值。`ge=-30, le=30` 表示**限制在 -30~30**(防 LLM 給分暴衝)。
- **ended**:LLM 自己判斷玩家是否提出讓它完全滿意的方案(成功的捷徑)。
- **emotion**:用 `Literal` **鎖死五個值**,LLM 不能亂回別的字,前端換立繪才不會出錯。
- **concession_cost**:由奧客大腦估「店員這一句讓掉多少成本/原則彈性」,範圍 **0~100**。判讀標準:**純同理、給資訊、設限、提替代方案 = 0**;小讓步(送小東西、打小折)= 10~30;大讓步(免單、退費、退一賠十、破例)= 40~100。這個欄位是「讓步成本」機制的源頭——它會被後端逐回合累加,最後讓評審算「成本控制分」,**懲罰無腦讓步**。

### JudgeReport:結算報告吐什麼

```python
class JudgeReport(BaseModel):
    empathy_score: int      # 同理心 0~100
    crisis_score: int       # 危機應變 0~100
    compliance_score: int   # 法規店規遵從 0~100
    good_practices: list[str]  # 做得好的話術
    bad_practices: list[str]   # 可改進的話術 + 建議
    summary: str               # 總評
```

三個分數 → 前端畫雷達圖;兩個 list → 列出好/壞話術;summary → 總評。

> 💡 **為什麼用 Pydantic 而不是自己解析 JSON?**
> 真實模式下用 `with_structured_output(CustomerTurn)`,會**強制** LLM 回這個結構,格式錯自動重試。後端拿到的一定是乾淨、型別正確的物件,不用手刻解析、不怕它多話。

## 2. state.py —— 整場遊戲的「共享筆記本」

`GameState` 是一個 `TypedDict`(本質就是規定好 key 的字典)。**所有節點都讀寫它**。分四類欄位:

```python
class GameState(TypedDict):
    # 【關卡靜態設定】開局載入,整場不變
    scenario_id: str
    scenario: dict           # 完整關卡設定(含結局台詞)
    system_prompt: str       # 組好的奧客角色卡
    max_turns: int           # 回合上限

    # 【動態狀態】每回合變化
    anger: int               # 當前憤怒值 0~100  ← 血條
    turn: int                # 已進行回合數
    messages: Annotated[list, add_messages]          # 對話歷史  ← 記憶
    anger_history:   Annotated[list, operator.add]   # 每回合憤怒值(含開局)← 軌跡
    emotion_history: Annotated[list, operator.add]   # 每回合奧客情緒        ← 軌跡

    # 【本回合 I/O】
    player_input: str        # 玩家這句話(語音輸入 STT 後 / 直接打字)
    voice_emotion: Optional[str]  # 玩家「語氣」情緒(來自 SER;打字回合為 None)
    ai_reply: str            # 奧客這句台詞
    anger_change: int        # 這回合憤怒變化
    emotion: str             # 這回合情緒
    concession_cost: int     # 這回合店員讓掉的成本(由奧客大腦估)
    cost_spent: int          # 本場累積讓步成本(每回合在 apply_state 累加)

    # 【結束相關】
    ended: bool
    ending_type: Optional[str]  # "fail"|"success"|"timeout"|None
    report: Optional[dict]      # 評審報告(只有結束才有)
```

### 為什麼要分這四類?
- **靜態設定**:開局一次填好,整場不動(角色是誰、回合上限)。
- **動態狀態**:跨回合會變、要被記住的(憤怒值、回合、歷史)。
- **本回合 I/O**:這一回合的暫存(這句輸入、玩家語氣、這句回應、這句的讓步成本)。
- **結束相關**:結局與報告。

> 💡 **新欄位重點**(讓步成本/語氣機制的承載):
> - **concession_cost**:本回合的暫存(這句讓掉多少),屬本回合 I/O。
> - **cost_spent**:**本場累積**讓步成本。雖然寫在 I/O 區,但它是「逐回合累加」的——`apply_state` 每回合把這句的 `concession_cost` 加上去(單值替換寫回,所以 resume 重跑不會重複累加)。結束時評審用它算「成本控制分」。
> - **voice_emotion**:玩家「語氣」(來自語音情緒辨識 SER),打字回合是 `None`;會餵給奧客大腦影響反應。

### ⭐ 最重要的一行:`messages` 的 reducer

```python
messages: Annotated[list, add_messages]
```

> 補充:`anger_history` / `emotion_history` 也用 reducer,但用的是 `operator.add`(list 相加=串接)。所以 `apply_state` 每回合回傳 `anger_history=[新值]`,就會自動接到舊 list 後面。這兩條「軌跡」放後端 state,會被 checkpointer 持久化(伺服器重啟可還原),也給評審看憤怒走勢(見學習_4/_5)。

- `add_messages` 叫 **reducer(合併規則)**。
- 意思:節點回傳新訊息時,LangGraph 會**自動「追加」**到舊歷史後面,而**不是覆蓋**。
- 其他欄位(像 `anger`)沒標 reducer → 回傳就是**直接覆蓋**。

這就是奧客「記憶」的底層機制:對話像滾雪球一樣越積越多。(第 4 課會講這些 messages 怎麼被送進 LLM。)

## 3. 兩者的關係

```
LLM 吐出 ──> CustomerTurn ──> 節點拆開,寫進 ──> GameState 的對應欄位
                                                  (anger_change, ai_reply, emotion,
                                                   ended, concession_cost)
```

`CustomerTurn` 是「LLM 的輸出包裝」,`GameState` 是「遊戲的總帳本」。節點負責把前者拆進後者(第 5 課細講)。

## 🎓 老師可能問

**Q:憤怒值存在哪裡?**
A:存在 `GameState` 的 `anger` 欄位,範圍 0~100,每回合由 `apply_state` 節點更新。

**Q:對話歷史怎麼存的?**
A:存在 `GameState.messages`,它用 `add_messages` reducer,所以每回合的新訊息會自動追加而非覆蓋,形成完整歷史。

**Q:你怎麼確保 LLM 回的格式正確?**
A:用 Pydantic 定義 `CustomerTurn`/`JudgeReport`,真實模式用 `with_structured_output` 強制 LLM 照這個 schema 回,格式錯會自動重試,所以後端拿到的一定是合法物件。

**Q:`emotion` 如果 LLM 回了你沒定義的值怎麼辦?**
A:不會發生,因為 `emotion` 是 `Literal` 的五個固定值,等於 enum,schema 會限制 LLM 只能從中選。

**Q:`concession_cost`(讓步成本)在做什麼?為什麼要它?**
A:它讓奧客大腦標記「店員這一句讓掉多少成本/原則彈性」(0~100,純同理=0、免單退費=40~100)。後端在 `apply_state` 把它逐回合累加成 `cost_spent`,結束時評審據此算「成本控制分」。目的是**懲罰無腦讓步**——你靠免單壓住憤怒雖然會贏,但成本控制分會很低,綜合分被拉下來,逼玩家學「不花錢也能安撫」。

**Q:`voice_emotion` 從哪來?打字玩家會有嗎?**
A:來自語音情緒辨識(SER 微服務),代表玩家講話的「語氣」(兇/平靜…),會餵給奧客大腦影響反應。打字回合沒有語音,所以是 `None`(細節見學習_8)。
