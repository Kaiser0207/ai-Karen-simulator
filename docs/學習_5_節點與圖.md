## 1. 節點是什麼?

一個節點 = 一個**純函式**:`讀 state → 做事 → 回傳要更新的欄位(dict)`。
LangGraph 會把回傳的 dict 合併進 state(`messages` 是追加,其他是覆蓋)。

## 2. 六個節點逐一拆解

### ① customer_brain —— 奧客大腦
```python
def customer_brain(state):
    turn = llm.customer_turn(
        system_prompt=state["system_prompt"], anger=state["anger"],
        messages=state["messages"], player_input=state["player_input"],
        voice_emotion=state.get("voice_emotion"),   # 玩家這句的「語氣」(SER),打字回合為 None
    )
    return {
        "ai_reply": turn.reply,
        "anger_change": turn.anger_change,
        "emotion": turn.emotion,
        "ended": turn.ended,
        "concession_cost": turn.concession_cost,     # 這句讓掉多少「成本」(免單/退費高、純同理 0)
        "messages": [HumanMessage(state["player_input"]), AIMessage(turn.reply)],
    }
```
- **做什麼**:呼叫服務層(第 4 課)拿到 `CustomerTurn`,拆進 state。
- **注意**:這裡把「玩家這句 + 奧客這句」追加進 `messages`(這就是歷史累積的地方)。
- **多傳 `voice_emotion`**:若玩家用語音輸入,前端會帶上 SER 辨出的語氣(Angry/Anxious/Happy/Neutral),讓奧客連「你怎麼說」一起反應(口氣兇 → 安撫打折還可能回嗆);打字回合為 None,不影響。
- **多回傳 `concession_cost`**:LLM 估這句店員「讓掉多少成本」(免單/退費高、折價/送中、純同理或設限為 0),給下一步累積成本用。

### ② apply_state —— 套用憤怒變化
```python
def apply_state(state):
    delta = max(-30, min(30, state["anger_change"]))     # 夾限(防暴衝/防作弊)
    if delta < 0:                                        # 只「衰減安撫」,不衰減惹怒
        resistance = float((state.get("scenario") or {}).get("calm_resistance", 1.0)) or 1.0
        delta = round(delta / resistance)               # 困難關(resistance>1)同一句好話降的怒氣較少
    new_anger = max(0, min(100, state["anger"] + delta)) # 血條夾 0~100
    cost = max(0, min(100, int(state.get("concession_cost", 0) or 0)))
    return {
        "anger": new_anger, "turn": state["turn"] + 1,
        "anger_history": [new_anger],                    # operator.add reducer 會自動串接
        "emotion_history": [state.get("emotion", "neutral")],
        "cost_spent": int(state.get("cost_spent", 0) or 0) + cost,  # 累積本場讓步成本
    }
```
- **重點**:LLM 給的 anger_change 只是「建議」,**真正改血條由這裡控制**,並回合 +1。
- ⭐ **難度的怒氣衰減(calm_resistance)**:依關卡縮放「安撫成功」的**負向 delta**——困難關(resistance>1)同一句好話降的怒氣較少;**被惹怒的正向 delta 不打折**(被踩雷一樣痛),所以困難關「好話沒那麼有效、壞話一樣傷」。
- ⭐ **累積讓步成本 `cost_spent`**:把上一步的 `concession_cost` 加總,代表「這場花了多少資源換和平」。注意是**單值替換寫回**(`舊值 + 本回合`),不是 reducer 累加,避免 LangGraph 在 resume(同回合重跑)時重複計算。
- 同時把這回合的憤怒值/情緒**累積進 `anger_history`/`emotion_history`**(後端 GameState 持久化,給評審看軌跡、伺服器重啟可還原)。

### ③ classify_ending —— 判斷結局
```python
def classify_ending(state):
    if state["anger"] >= 100:        et = "fail"     # 爆表最優先
    elif state["ended"]:             et = "success"  # 由 LLM 判定「完美方案/和解」
    elif state["turn"] >= state["max_turns"]:   et = "timeout"
    else:                            et = None
    return {"ending_type": et}
```
- **做什麼**:依優先序判斷結局類型,**寫進 state**。優先級:fail > success > timeout > None。
- ⚠️ **成功只看 `ended`(LLM 判定),不再用「血條歸零」自動算成功**:血條低只代表顧客冷靜,不等於問題解決、願意和解,所以交給 LLM 判斷玩家是否真的提出完美方案。
- ⭐ **為什麼是獨立節點(踩過的雷)**:LangGraph 的「岔路判斷函式」回傳值**只能選邊、不會寫進 state**。如果在岔路直接決定結局,後面 `set_ending` 讀不到。所以拆成「節點寫 → 岔路讀」。

### ④ route_after_classify —— 岔路(這是邊,不是節點)
```python
def route_after_classify(state):
    return "continue" if state["ending_type"] is None else "ending"
```
- 只**讀** state 決定走哪條邊。

### ⑤ set_ending —— 收尾、播結局台詞
```python
def set_ending(state):
    line = state["scenario"].get("ending_lines", {}).get(state["ending_type"]) or "(對話結束。)"
    return {"ended": True,
            "emotion": _ENDING_EMOTION.get(state["ending_type"], "neutral"),
            "messages": [AIMessage(line)]}
```
- **做什麼**:從 scenario 取**預寫好的結局台詞**(第 3 課)附加進對話,標記結束。
- 用 `.get(...) or 通用句` 防禦:萬一關卡缺該結局台詞,退一句通用收尾而非 KeyError 崩潰。

### ⑥ judge —— 評審大腦
```python
def judge(state):
    budget = int(state["scenario"].get("cost_budget", 80) or 80)
    cost_spent = int(state.get("cost_spent", 0) or 0)
    report = llm.judge_report(
        state["messages"],
        ending_type=state["ending_type"],          # 把結局與軌跡一起給評審
        anger_history=state.get("anger_history"),   # → 讓評分呼應勝負,不矛盾
        max_turns=state["max_turns"],
        cost_spent=cost_spent, cost_budget=budget,  # 把讓步成本一起給評審
    )
    data = report.model_dump()                      # 把 Pydantic 物件轉字典
    data["cost_control_score"] = _cost_control_score(cost_spent, budget)  # 後端公式算「成本控制分」覆寫進報告
    data["cost_spent"] = cost_spent                 # 附原始數字供前端顯示
    data["cost_budget"] = budget
    return {"report": data}
```
- **做什麼**:呼叫評審(第 4 課),把報告轉成 dict 存進 state(`model_dump()` 把 Pydantic 物件轉字典)。
- **outcome-aware**:連同結局類型、憤怒軌跡與**讓步成本**一起傳給評審,避免「顧客爆走卻誇店員處理優秀」「照單全收狂讓步卻給高分」的矛盾。
- ⭐ **成本控制分由後端算**:`cost_control_score` 不交給 LLM 自由發揮,而是用一條**確定性公式**(`_cost_control_score`:預算內 100→75、超支再線性降到 0)算好後**覆寫**進報告——穩定、可解釋,讓「無腦讓步」成本爆表時這項分數明顯被拉低。成本數字也一併附進報告供前端顯示。

## 3. build.py —— 把節點串成圖

```python
def build_graph(checkpointer):
    g = StateGraph(GameState)
    g.add_node("customer_brain", customer_brain)
    g.add_node("apply_state", apply_state)
    g.add_node("classify_ending", classify_ending)
    g.add_node("set_ending", set_ending)
    g.add_node("judge", judge)

    g.add_edge(START, "customer_brain")
    g.add_edge("customer_brain", "apply_state")
    g.add_edge("apply_state", "classify_ending")
    g.add_conditional_edges("classify_ending", route_after_classify, {
        "continue": END,           # 沒結束 → 結束本次 invoke,等下一句
        "ending":   "set_ending",  # 結束 → 播台詞 → 評審
    })
    g.add_edge("set_ending", "judge")
    g.add_edge("judge", END)
    return g.compile(checkpointer=checkpointer)
```

### 圖的形狀
```
START → customer_brain → apply_state → classify_ending ─┬─[continue]→ END
                                                        └─[ending]→ set_ending → judge → END
```

- 大部分是**固定邊**(做完 A 一定到 B)。
- 只有 `classify_ending` 後面是**條件邊**(岔路),由 `route_after_classify` 決定。
- `checkpointer` 參數就是記憶(第 6 課接)。

---

## 4. ⭐「一次 invoke = 一個回合」

注意:**沒結束就走到 END 了**。下一句玩家輸入會「**從 START 再跑一次整張圖**」,但因為 checkpointer 記得上次的 state,憤怒值和歷史都接得上。
所以「多回合」不是靠圖內部迴圈,而是靠「**外部一直 invoke + 記憶**」。

## 🎓 老師可能問

**Q:結局怎麼判定?**
A:`classify_ending` 節點依優先序檢查:憤怒≥100→失敗、**LLM 判定和解(ended=True)→成功**、回合用完→超時、否則繼續。注意成功**只看 LLM 的 ended**,血條歸零不再自動算成功(血條低只代表顧客冷靜)。結果寫進 state,再由條件邊決定走「繼續」或「收尾+評審」。

**Q:為什麼不把判定寫在岔路函式就好?**
A:因為 LangGraph 岔路函式的回傳值只用來選邊、不會寫進 state,後面 set_ending 需要從 state 讀結局類型才能取對應台詞。所以拆成「節點寫狀態 + 岔路讀狀態」。這是我實作時踩到的雷。

**Q:LLM 亂給很高的 anger_change 會怎樣?**
A:不會失控。`apply_state` 把它硬夾在 ±30,血條再夾 0~100。LLM 只能建議,後端決定實際變化。

**Q:遊戲怎麼進行多個回合?**
A:每次玩家輸入就 invoke 一次整張圖(=一回合),沒結束就到 END;靠 checkpointer 以 thread_id 保存 state,下次 invoke 自動接續憤怒值與歷史。

**Q:「讓步成本」是什麼?在哪裡算、評分怎麼用?**
A:每回合 customer_brain 由 LLM 估這句店員「讓掉多少成本」(`concession_cost`:免單/退費高、折價/送中、純同理 0),apply_state 累積成 `cost_spent`。結束時 judge 用後端確定性公式把 `cost_spent` 對 `cost_budget` 換成 `cost_control_score`(成本控制分)覆寫進報告。設計目的:讓「照單全收、無腦讓步」雖然可能讓顧客滿意,但成本控制分會被拉低,鼓勵用同理+設限低成本化解。

**Q:同一句好話,在簡單關和困難關效果一樣嗎?**
A:不一樣。apply_state 會依關卡的 `calm_resistance` 縮放**安撫成功的負向 delta**——困難關同一句好話降的怒氣較少;但**被惹怒的正向 delta 不打折**(壞話一樣傷)。所以困難關「好話沒那麼有效、踩雷一樣痛」。
