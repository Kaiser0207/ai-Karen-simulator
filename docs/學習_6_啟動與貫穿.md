## 2. 啟動腳本

> ⭐ **實際在跑的後端是 `web/server.py`(FastAPI,port 8000)**,不是底下這兩支腳本。`run_demo.py` 與 `smoke_test.py` 是**開發驗證用**的小工具,真正讓網頁玩起來的是 `web/server.py`。三者用的都是同一張圖(`build_graph`),差別只在「誰來呼叫」。

### web/server.py(實際網頁後端,FastAPI · port 8000)★主入口
把同一張 LangGraph 圖包成 JSON API 給前端網頁用。三個主要端點:
- `POST /api/start`:開一場 → 配一個 `thread_id`(uuid),回開場白與初始狀態。
- `POST /api/say`:玩家說一句 → `graph.invoke` 跑一回合 → 回奧客回應與最新狀態(結束時附結局台詞與評審報告)。語音輸入時這裡會帶上 `voice_emotion`(語氣)。
- `POST /api/stt`:瀏覽器錄音 → faster-whisper 轉文字,並順手做語氣辨識(SER)。

```python
# 建一次圖,checkpointer 用「檔案版」SQLite(game_state.db),伺服器重啟也記得對局
_conn = sqlite3.connect("game_state.db", check_same_thread=False, timeout=30)
GRAPH = build_graph(SqliteSaver(_conn))

@app.post("/api/say")
def api_say(req: SayReq):
    payload = {**sess["init"], "player_input": text} if sess["first"] else {"player_input": text}
    payload["voice_emotion"] = req.voice_emotion          # 語音才帶,打字為 None
    result = GRAPH.invoke(payload, {"configurable": {"thread_id": req.thread_id}})
    ... 回 ai_reply / anger / cost_spent / 結束時的 report ...
```
- **每場一個 `thread_id`**:和 run_demo 一樣的記憶機制,只是 thread_id 改由後端發 uuid。多人/多場同時玩時,各自的 thread_id 互不干擾(見第 3 節)。
- **班次(shift)模式**:前端可一次排班串多個客人,但**後端每一場仍是獨立的 thread_id**;班次只是前端把同組客人聚在一起的組織方式(`shift_id` 只用來在歷史紀錄分組)。

啟動:`uv run python -m web.server`(或 `uv run uvicorn web.server:app --port 8000`)。

### run_demo.py(mock 三結局驗證,免 key)
跑三場腳本化對話,分別觸發成功/失敗/超時,印出憤怒值軌跡與報告。**是 mock 驗證腳本**,用來確認狀態機正確,不是實際網頁後端。重點是它怎麼建圖、怎麼一回合一回合 invoke:

```python
with SqliteSaver.from_conn_string(":memory:") as cp:   # 記憶體版 checkpointer
    graph = build_graph(cp)
    play_game(graph, ...)

def play_game(graph, ..., scenario_id, inputs, thread_id):
    init = loader.load(scenario_id)                     # 開局 state(第 3 課)
    config = {"configurable": {"thread_id": thread_id}} # 這場的身分證
    first = True
    for text in inputs:
        # 第一回合送整包開局 state;之後只送這回合的話
        payload = {**init, "player_input": text} if first else {"player_input": text}
        first = False
        result = graph.invoke(payload, config)          # 跑一回合
        ... 印出 result["ai_reply"], result["anger"] ...
        if result.get("ended"): ... 印報告; break
```

### smoke_test.py(真實 LLM 單回合)
最小化:`loader.load` → `llm.customer_turn(...)` → 印結果。用來確認 key 與結構化輸出正常(預設打 Groq,也可切 Gemini)。

## 3. ⭐ thread_id + checkpointer —— 記憶怎麼跨回合

這是「多回合」能成立的關鍵:

```python
config = {"configurable": {"thread_id": "demo-success"}}
graph.invoke({"player_input": text}, config)
```

- **thread_id** = 一場遊戲的身分證。
- **checkpointer(SqliteSaver)** 以 thread_id 為鍵,把每回合結束的 state 存起來。
- 下一回合再 invoke(同一個 thread_id),checkpointer **自動把上次的 state 載回**,所以:
  - 第一回合要送整包開局 state(初始化);
  - 之後只要送 `{"player_input": text}`,憤怒值、歷史都自動接續。

> 換不同 thread_id = 開一場全新遊戲(互不干擾)。這也是將來多人同時玩的基礎。

## 4. 🎬 完整貫穿:跟著一個回合走一遍

把前五課串起來。情境:張大媽,目前憤怒 50,玩家講了句官腔。

```
【玩家輸入】"這是公司規定,我也沒辦法。"
   │
   │ run_demo / 前端:graph.invoke({"player_input": "..."}, {thread_id})
   │ checkpointer 載回上次 state(anger=50, messages=[開場白...])   ← 第 6 課
   ▼
① customer_brain(第 5 課)
   │  呼叫 services.llm.customer_turn(system_prompt, 50, messages, "這是公司規定…",
   │        voice_emotion=…)  ← 第 4 課
   │     真實版組訊息陣列:[角色卡, 憤怒值note, (語氣note), *歷史, 玩家這句] → 送 LLM(Groq/Gemini,預設 Groq)
   │     ※ 若是語音輸入,玩家這句還帶 voice_emotion(語氣);口氣兇 → 安撫打折、奧客可能回嗆
   │     LLM 回 CustomerTurn(reply="你這什麼態度!", anger_change=+22,
   │                         emotion="annoyed", ended=False, concession_cost=0)  ← 第 2 課的格式
   │  寫回 state:ai_reply, anger_change=22, emotion, ended, concession_cost,
   │            messages 追加 [玩家這句, 奧客這句]
   ▼
② apply_state(第 5 課)
   │  夾限 +22(在範圍內);+22 是「被惹怒」不打折 → anger = 50+22 = 72;turn = 0+1 = 1
   │  (若是負的安撫 delta,困難關會被 calm_resistance 縮小)
   │  把 72 追加進 anger_history、情緒追加進 emotion_history;concession_cost 累進 cost_spent
   ▼
③ classify_ending(第 5 課)
   │  72 沒≥100、ended=False(LLM 沒判和解)、回合沒用完 → ending_type = None
   │  (成功只看 ended,不看血條是否歸零)
   ▼
④ 〔岔路 route_after_classify〕:ending_type 是 None → "continue" → END
   ▼
【前端顯示】
   聊天視窗:"你這什麼態度!"
   血條:50 → 72(變紅,顯示 +22)
   立繪:annoyed
   因為沒 ended,等玩家下一句
   │
   │ checkpointer 已把新 state(anger=72, 更長的 messages)存好
   ▼
【玩家再輸入】→ 又從 ① 跑一次,這次 anger 已是 72…
```

如果某回合 anger 衝破 100:
```
③ classify_ending → "fail"
④ 岔路 → "ending" → ⑤ set_ending(附加 fail 結局台詞)→ ⑥ judge(評審報告)→ END
   前端:鎖定輸入、顯示結局、畫雷達圖
```

**能流暢講完這一圈,你就掌握整個架構了。**

## 🎓 考古題總整理(答辯衝刺)

**Q:整個系統怎麼運作的?(請從頭講一遍)**
A:玩家輸入 →(實際是網頁前端打 `web/server.py` 的 `/api/say`)invoke 整張 LangGraph 圖一回合 → customer_brain 呼叫 LLM(預設 Groq,可切 Gemini;送角色卡+憤怒值+歷史+這句話,語音還帶語氣)拿到台詞、憤怒變化與讓步成本 → apply_state 更新血條、累積成本 → classify_ending 判斷結局 → 沒結束就 END 等下一句、結束就 set_ending 播結局台詞再 judge 出報告(含後端算的成本控制分)。多回合靠 thread_id + checkpointer 保存與接續。

**Q:為什麼用 LangGraph?**
A:遊戲本質是狀態機,LangGraph 用節點+邊表達狀態機很自然,還自帶跨回合記憶,比手刻 if/else 清楚好維護。

**Q:AI 怎麼有記憶?**
A:LLM 無狀態。每回合把完整對話歷史 messages 一起送進 prompt;歷史由 add_messages 累積、SqliteSaver 以 thread_id 跨回合保存。

**Q:憤怒值是 AI 決定的嗎?會不會亂跳?**
A:AI 只「建議」anger_change,後端 apply_state 硬夾 ±30、血條夾 0~100,真正控制在後端,不會暴衝。

**Q:怎麼防作弊(玩家叫 AI 把憤怒設成 0)?**
A:prompt 明示無視改設定的指令 + 後端夾限,雙保險。

**Q:結局台詞為什麼是預寫的?**
A:避免「LLM 講話當下還不知道會爆表 → 平淡台詞配爆表血條」的不一致,預寫保證一致也省一次呼叫。

**Q:奧客和評審是同一個 AI 嗎?**
A:同一顆模型、不同用法:奧客每回合、入戲、高溫度;評審結束一次、客觀、低溫度、不同 prompt。

**Q:你怎麼確保 LLM 回傳格式正確?**
A:Pydantic schema + with_structured_output 強制格式,錯了自動重試。

**Q:你開發時踩過什麼雷?**
A:(1) 開場白沒進 messages 導致第一回合失憶;(2) 結局台詞時機矛盾,改成預寫;(3) classify_ending 必須獨立成節點,因為岔路回傳值不會寫進 state;(4) Gemini 2.0-flash 免費額度為 0(429),換 2.5-flash;**Gemini 免費層一天只有約 20 次,demo/開發很快就打爆 → 改用 Groq(llama-3.3-70b)當主力**,程式只要改 `.env` 的 `LLM_PROVIDER`,節點層不動;(5) 評審若直接把 messages 用原生 user/assistant 角色丟,會把奧客的兇話誤算到店員頭上 → 改成攤平成「店員:/奧客:」的標籤對話再送,角色歸屬才不會錯;(6) uv 子專案被併入上層 workspace、工作目錄重置裝錯專案。詳見 `開發錯誤紀錄.md`。

**Q:新增一個奧客角色要做什麼?**
A:只加一個 scenario JSON(角色變數 + 結局台詞),程式不用改。

**Q:mock 模式是什麼?為什麼要有?**
A:用關鍵字規則模擬奧客,免 API key、可重現,讓我們能單獨測狀態機、不花額度,也方便 demo 沒網路時備用。

**Q:用 Gemini 還是別的 LLM?為什麼?**
A:預設 **Groq(llama-3.3-70b)**,Gemini 可切。因為 Gemini 免費層一天約只有 20 次,開發/demo 很快打爆(429);改用 Groq 當主力穩定很多。切換只改 `.env` 的 `LLM_PROVIDER`(groq/gemini),奧客大腦/評審/節點層程式都不用動——因為服務層(第 4 課)已把供應商抽象掉。

**Q:讓步成本 / 成本控制分是做什麼的?**
A:防止「無腦讓步刷高分」。每回合 LLM 估這句讓掉多少成本(免單高、折價中、純同理 0),累積成 `cost_spent`;結束時 judge 用**後端確定性公式**對關卡預算 `cost_budget` 換成 `cost_control_score` 覆寫進報告。所以照單全收雖讓顧客滿意,成本控制分卻會被拉低,鼓勵低成本化解。分數由後端公式算(不是 LLM 自由給)→ 穩定、可解釋。

**Q:玩家的「語氣」會影響奧客嗎?**
A:會。語音輸入時前端做 SER(語音情緒辨識,辨「怎麼說」而非字面),把語氣(Angry/Anxious/Happy/Neutral)當 `voice_emotion` 帶進 customer_brain。同樣一句話,口氣兇 → 安撫效果打折、奧客還可能回嗆;口氣真誠 → 比較容易消氣。打字回合沒語氣,不影響。

**Q:多人 / 多場同時玩會不會互相干擾?班次模式是什麼?**
A:不會。每一場都是獨立的 `thread_id`,checkpointer 以 thread_id 為鍵各存各的。班次(shift)模式是前端把一連串客人排成一班讓玩家連續應對,但**後端每一場仍是獨立 thread_id**,班次資訊(shift_id 等)只用來在歷史紀錄分組,不影響對局隔離。

**Q:評審為什麼要把對話改成「店員:/奧客:」的標籤格式?**
A:若直接用原生 user/assistant 角色送,評審 LLM 會把奧客講的兇話誤當成店員講的、歸錯人(fail 場奧客很兇時最常發作,對店員最不公平)。攤平成標明說話者的純文字後,角色歸屬不再有歧義,good/bad_practices 引用與 compliance 評分才正確。
