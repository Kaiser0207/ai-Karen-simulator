## 2. 啟動腳本

### run_demo.py(mock 三結局驗證,免 key)
跑三場腳本化對話,分別觸發成功/失敗/超時,印出憤怒值軌跡與報告。重點是它怎麼建圖、怎麼一回合一回合 invoke:

```python
with SqliteSaver.from_conn_string(":memory:") as cp:   # 記憶體版 checkpointer
    graph = build_graph(cp)
    play_game(graph, ...)

def play_game(graph, ..., scenario_id, inputs, thread_id):
    init = loader.load(scenario_id)                     # 開局 state(第 3 課)
    config = {"configurable": {"thread_id": thread_id}} # 這場的身分證
    first = True
    for text in inputs:
        # 第一回合送整包開局 state;之後只送這回合的話
        payload = {**init, "player_input": text} if first else {"player_input": text}
        first = False
        result = graph.invoke(payload, config)          # 跑一回合
        ... 印出 result["ai_reply"], result["anger"] ...
        if result.get("ended"): ... 印報告; break
```

## 3. ⭐ thread_id + checkpointer —— 記憶怎麼跨回合

這是「多回合」能成立的關鍵:

```python
config = {"configurable": {"thread_id": "demo-success"}}
graph.invoke({"player_input": text}, config)
```

- **thread_id** = 一場遊戲的身分證。
- **checkpointer(SqliteSaver)** 以 thread_id 為鍵,把每回合結束的 state 存起來。
- 下一回合再 invoke(同一個 thread_id),checkpointer **自動把上次的 state 載回**,所以:
  - 第一回合要送整包開局 state(初始化);
  - 之後只要送 `{"player_input": text}`,憤怒值、歷史都自動接續。

> 換不同 thread_id = 開一場全新遊戲(互不干擾)。這也是將來多人同時玩的基礎。

## 4. 🎬 完整貫穿:跟著一個回合走一遍

把前五課串起來。情境:張大媽,目前憤怒 50,玩家講了句官腔。

```
【玩家輸入】"這是公司規定,我也沒辦法。"
   │
   │ run_demo / 前端:graph.invoke({"player_input": "..."}, {thread_id})
   │ checkpointer 載回上次 state(anger=50, messages=[開場白...])   ← 第 6 課
   ▼
① customer_brain(第 5 課)
   │  呼叫 services.llm.customer_turn(system_prompt, 50, messages, "這是公司規定…")  ← 第 4 課
   │     真實版組訊息陣列:[角色卡, 憤怒值note, *歷史, 玩家這句] → 送 Gemini
   │     Gemini 回 CustomerTurn(reply="你這什麼態度!", anger_change=+22,
   │                            emotion="annoyed", ended=False)    ← 第 2 課的格式
   │  寫回 state:ai_reply, anger_change=22, emotion, ended,
   │            messages 追加 [玩家這句, 奧客這句]
   ▼
② apply_state(第 5 課)
   │  夾限 +22(在範圍內)→ anger = 50+22 = 72;turn = 0+1 = 1
   │  並把 72 追加進 anger_history、情緒追加進 emotion_history(軌跡)
   ▼
③ classify_ending(第 5 課)
   │  72 沒≥100、ended=False(LLM 沒判和解)、回合沒用完 → ending_type = None
   │  (成功只看 ended,不看血條是否歸零)
   ▼
④ 〔岔路 route_after_classify〕:ending_type 是 None → "continue" → END
   ▼
【前端顯示】
   聊天視窗:"你這什麼態度!"
   血條:50 → 72(變紅,顯示 +22)
   立繪:annoyed
   因為沒 ended,等玩家下一句
   │
   │ checkpointer 已把新 state(anger=72, 更長的 messages)存好
   ▼
【玩家再輸入】→ 又從 ① 跑一次,這次 anger 已是 72…
```

如果某回合 anger 衝破 100:
```
③ classify_ending → "fail"
④ 岔路 → "ending" → ⑤ set_ending(附加 fail 結局台詞)→ ⑥ judge(評審報告)→ END
   前端:鎖定輸入、顯示結局、畫雷達圖
```

**能流暢講完這一圈,你就掌握整個架構了。**

## 🎓 考古題總整理(答辯衝刺)

**Q:整個系統怎麼運作的?(請從頭講一遍)**
A:玩家輸入 → invoke 整張 LangGraph 圖一回合 → customer_brain 呼叫 Gemini(送角色卡+憤怒值+歷史+這句話)拿到台詞與憤怒變化 → apply_state 更新血條 → classify_ending 判斷結局 → 沒結束就 END 等下一句、結束就 set_ending 播結局台詞再 judge 出報告。多回合靠 thread_id + checkpointer 保存與接續。

**Q:為什麼用 LangGraph?**
A:遊戲本質是狀態機,LangGraph 用節點+邊表達狀態機很自然,還自帶跨回合記憶,比手刻 if/else 清楚好維護。

**Q:AI 怎麼有記憶?**
A:LLM 無狀態。每回合把完整對話歷史 messages 一起送進 prompt;歷史由 add_messages 累積、SqliteSaver 以 thread_id 跨回合保存。

**Q:憤怒值是 AI 決定的嗎?會不會亂跳?**
A:AI 只「建議」anger_change,後端 apply_state 硬夾 ±30、血條夾 0~100,真正控制在後端,不會暴衝。

**Q:怎麼防作弊(玩家叫 AI 把憤怒設成 0)?**
A:prompt 明示無視改設定的指令 + 後端夾限,雙保險。

**Q:結局台詞為什麼是預寫的?**
A:避免「LLM 講話當下還不知道會爆表 → 平淡台詞配爆表血條」的不一致,預寫保證一致也省一次呼叫。

**Q:奧客和評審是同一個 AI 嗎?**
A:同一顆模型、不同用法:奧客每回合、入戲、高溫度;評審結束一次、客觀、低溫度、不同 prompt。

**Q:你怎麼確保 LLM 回傳格式正確?**
A:Pydantic schema + with_structured_output 強制格式,錯了自動重試。

**Q:你開發時踩過什麼雷?**
A:(1) 開場白沒進 messages 導致第一回合失憶;(2) 結局台詞時機矛盾,改成預寫;(3) classify_ending 必須獨立成節點,因為岔路回傳值不會寫進 state;(4) Gemini 2.0-flash 免費額度為 0(429),換 2.5-flash;(5) uv 子專案被併入上層 workspace、工作目錄重置裝錯專案。詳見 `開發錯誤紀錄.md`。

**Q:新增一個奧客角色要做什麼?**
A:只加一個 scenario JSON(角色變數 + 結局台詞),程式不用改。

**Q:mock 模式是什麼?為什麼要有?**
A:用關鍵字規則模擬奧客,免 API key、可重現,讓我們能單獨測狀態機、不花額度,也方便 demo 沒網路時備用。
