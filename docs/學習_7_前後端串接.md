這個專案有**兩套前端**,後端的圖**完全共用同一份**:

## 1. 最重要的觀念:這次是「真的兩端 + HTTP」

主力前端是**瀏覽器裡的原生 JS**(不是 Python),它**沒辦法直接 `import` 後端的函式**。所以中間一定要有一層 **HTTP API**:

```
        瀏覽器(web/static)                  伺服器(web/server.py)
┌──────────────────────────┐         ┌──────────────────────────────┐
│ index.html + app.js      │  HTTP   │  FastAPI                      │
│  按鈕/輸入框/語音        │ ──────▶ │   @app.post("/api/say")       │
│   │ fetch("/api/say")    │  JSON   │     │ graph.invoke(...) ←後端的圖│
│   ▼                      │ ◀────── │     ▼ 回 JSON                 │
│  把回傳 JSON 畫到畫面    │         │  graph/ services/ scenarios/  │
└──────────────────────────┘         └──────────────────────────────┘
```

- 前端用瀏覽器內建的 **`fetch()`** 打 `/api/*`,送/收 **JSON**。
- 後端 FastAPI 收到請求,**在伺服器這邊**呼叫 `graph.invoke(...)`,把結果包成 JSON 回傳。
- 兩邊用「HTTP + JSON 合約」溝通,各自獨立——這正是當初把邏輯放後端、與前端解耦的好處。

> 📌 對照:Gradio(`app.py`)因為**也是 Python**,前後端在同一程式裡,可以直接呼叫 `GRAPH.invoke`,不需要 HTTP(更單純,但綁死 Python 前端)。**第 8 課之外、本課第 7 節有完整對照。**

## 2. 前後端的「連接合約」其實還是那 4 件事

不管用 HTTP 還是直接呼叫,**對後端的需求一模一樣**——列關卡、開局、跑一回合、讀結果。差別只在「怎麼把這 4 件事傳過去」。

| 合約(要做的事) | web/ 主力:前端 `fetch` → FastAPI 端點 | Gradio 備援:直接呼叫 |
|---|---|---|
| ① 列出關卡 | `GET /api/scenarios` | `loader.list_scenarios()` |
| ② 開一場遊戲 | `POST /api/start` | `loader.load(scenario_id)` |
| ③ 跑一回合 | `POST /api/say` | `GRAPH.invoke(payload, config)` |
| ④ 讀結果更新畫面 | 讀回傳 JSON 的 `anger`/`ai_reply`/`ended`/`report` | 讀 `result["anger"]` … |

**前端做的事 = 收集輸入 → `fetch` 上面這幾個端點 → 把回傳 JSON 畫到畫面。** 就這樣。

## 3. 後端導覽:`web/server.py`(FastAPI 薄層)

這支檔案的定位很清楚(看它開頭的 docstring):**「把遊戲的 LangGraph 後端包成 JSON API」**,只負責「HTTP ↔ `graph.invoke`」與工作階段管理。

### (A) 啟動時:一樣只建一次圖

```python
_conn = sqlite3.connect("game_state.db", check_same_thread=False, timeout=30)
_conn.execute("PRAGMA journal_mode=WAL")
GRAPH = build_graph(SqliteSaver(_conn))
```

- **整個程式只建一次圖**,所有玩家共用(跟 Gradio 一樣)。
- `check_same_thread=False`:FastAPI/uvicorn 用 **threadpool** 跑同步端點,SQLite 連線預設綁單一執行緒,要關掉這限制。
- 比 Gradio 版多了兩個強化:`timeout=30`(被鎖時最多等 30 秒,而非立刻拋 `database is locked`)+ `WAL`(讀寫併發較友善)。
- 還加了一把 **`_DB_LOCK`**:單一連線多執行緒下共用同一 cursor 不安全,用鎖把 `graph` 的讀寫**序列化**(訓練工具併發極低,最簡單安全)。

### (B) session 狀態:用記憶體 dict `SESSIONS`(以 thread_id 為 key)

Gradio 是用 `gr.State`(每個瀏覽器分頁各一份)。**自訂前端沒有 `gr.State`**,所以後端自己用一個 dict 記每場的附加資訊:

```python
SESSIONS: dict[str, dict] = {}   # thread_id -> {"init":…, "first":True/False, "scenario":…, "last":時間, 班次資訊…}
```

- **真正的 graph state(憤怒值、歷史、訊息)由 `SqliteSaver` checkpointer 以 thread_id 持久化**;`SESSIONS` 只記「是不是首回合」「哪個關卡」「最後活動時間」「班次資訊」這些殼層資訊。
- 有 **TTL 垃圾回收**(`_SESSION_TTL = 3600`):玩家中離後,閒置過久就清掉記憶體 session,不永久佔記憶體。

### (C) `_get_session`:記憶體沒有時,從 checkpointer 還原(答辯亮點 ⭐)

這是 Gradio 版沒有的設計,務必記熟:

```python
def _get_session(thread_id):
    # 1) 記憶體 SESSIONS 有 → 直接用
    # 2) 沒有(伺服器重啟 / TTL 清掉)→ 查 checkpointer 的 graph state
    snap = GRAPH.get_state({"configurable": {"thread_id": thread_id}})
    vals = snap.values
    if not vals or not vals.get("scenario"):
        return None                 # 從沒開始過 → 真的不存在
    if vals.get("ended"):
        return None                 # ⭐ 已結束 → 當作不存在(見下)
    return {"first": False, "scenario": vals["scenario"], …}  # 還原成可繼續玩
```

兩個關鍵防呆:
1. **伺服器重啟後對局還能續玩**:只要該 thread 跑過至少一回合,graph state 還在 SqliteSaver,就能還原關卡並以 `first=False` 接著玩(記憶體丟了不要緊)。
2. **已結束的對局擋掉重送**:`/api/say` 結束時會 `SESSIONS.pop`,但 checkpointer **永久保留**那場 state。若不擋,同一 thread_id 再來一個 `/api/say`(連點、網路重送、多分頁)會被「還原成可繼續玩」,於是**再跑一次 graph → 又呼叫一次評審 LLM(白花額度)+ 覆寫汙染歷史紀錄**。所以 `ended` 就回 `None` → `/api/say` 直接 **404「工作階段不存在或已結束」**。

### (D) 三個核心端點 = 前端的入口

```python
@app.get("/api/scenarios")     # ① 列關卡(給選關卡卡片)
@app.post("/api/start")        # ② 開局:建 thread_id、回開場白與初始 state
@app.post("/api/say")          # ③ 跑一回合:player_input → graph.invoke → 回 JSON
```

**`POST /api/start`**(對應 Gradio 的 `start_game`):
```python
init = loader.load(req.scenario_id)
sid  = uuid.uuid4().hex                       # 給這場一個 thread_id
SESSIONS[sid] = {"init": init, "first": True, "scenario": init["scenario"], …}
return {"thread_id": sid, "opening_line": …, "anger": …, "max_turns": …, "scenario": {…}}
```
> 注意:**thread_id 由後端產生並回傳給前端**(Gradio 是前端 `gr.State` 自己存)。前端拿到後存在 JS 的 `STATE.thread`,之後每次 `/api/say` 都帶上。

**`POST /api/say`**(對應 Gradio 的 `player_say`)——本課最核心:
```python
sess = _get_session(req.thread_id)            # 取/還原 session;沒有或已結束 → 404
if not sess: raise HTTPException(404, …)

payload = {**sess["init"], "player_input": text} if sess["first"] else {"player_input": text}
payload["voice_emotion"] = req.voice_emotion  # 語音才有語氣,打字為 None
result = GRAPH.invoke(payload, {"configurable": {"thread_id": req.thread_id}})  # ← 呼叫後端的圖!
SESSIONS[req.thread_id].update(first=False, …)

resp = {"ai_reply": result["ai_reply"], "anger": result["anger"], "turn": result["turn"],
        "ended": bool(result.get("ended")), "ending_type": result.get("ending_type"), …}
if resp["ended"]:
    resp["report"] = result["report"]; resp["ending_line"] = …
    storage.save_game(…)                      # ⭐ 對局結束 → 存進歷史頁
    SESSIONS.pop(req.thread_id, None)          # 清掉記憶體 session(checkpointer 仍永久保留)
return resp
```

**這就是「同程式直接呼叫」與「HTTP API」唯一真正的差別**:外面多了 `req`(收 JSON)、`resp`(回 JSON)、HTTP 狀態碼(404/400/503)這層殼,**但中間那行 `GRAPH.invoke(...)` 跟 Gradio 版一字不差**。

### (E) 其餘端點(第 8 課細講)

- `GET /api/history`、`GET /api/history/{thread_id}`:讀 `storage` 的歷史紀錄(對局結束時存的)。
- `POST /api/stt`:瀏覽器錄音 → faster-whisper 轉繁中文字(+ SER 語氣)→ 回 `{text, emotion}`,前端填進輸入框。
- 最後兩行 `app.mount("/", StaticFiles(..., html=True))` **把 `web/static/` 整包當靜態網頁送**(放最後,`/api/*` 路由才會優先比對)。所以同一個 8000 port **既出網頁、又出 API**。

## 4. 前端導覽:`web/static/app.js`(原生 JS)

沒有 Gradio 元件,所有 UI 都自己用 JS 操作 DOM。對後端的呼叫全都走一個共用的 `api()` 包一層 `fetch`:

```javascript
async function api(path, opts) {
  const res = await fetch(path, opts);                 // 打 /api/*
  if (!res.ok) { ...throw new Error(detail); }          // 後端的 4xx/5xx → 取 detail 顯示
  return await res.json();                               // 成功 → 解析 JSON
}
```
- 還內建 `AbortController` **逾時**:AI 卡住時 UI 不會永遠「思考中」(`/api/say` 給 90 秒、`/api/start` 45 秒)。

**前端如何呼叫各端點:**

| 行為 | 前端程式 | 打哪個端點 |
|---|---|---|
| 進首頁載關卡 | `loadScenarios()` → `api("/api/scenarios")` | `GET /api/scenarios` |
| 點「開始挑戰」 | `startCustomer()` → `api("/api/start", {method:"POST", body: JSON.stringify({scenario_id,…})})` | `POST /api/start` |
| 送出一句話 | `send()` → `api("/api/say", {method:"POST", body: JSON.stringify({thread_id, text, voice_emotion})})` | `POST /api/say` |
| 語音輸入 | `toggleMic()` → `api("/api/stt", {method:"POST", body: FormData})` | `POST /api/stt` |
| 進歷史頁 | `loadHistory()` / `viewHistory(tid)` → `api("/api/history…")` | `GET /api/history` |

**前端怎麼記 thread_id**:`/api/start` 回來後存進全域 `STATE.thread`(取代 Gradio 的 `gr.State`),之後 `send()` 每次都把它放進 `/api/say` 的 body:
```javascript
const d = await api("/api/say", { method:"POST",
  body: JSON.stringify({ thread_id: STATE.thread, text, voice_emotion }) });
addMessage("bot", d.ended ? d.ending_line : d.ai_reply, "奧客");   // 把回傳畫到畫面
updateMeter(d.anger, d.turn, d.max_turns);                          // 更新血條
if (d.ended) finishCustomer(d);                                     // 結束 → 出報告
```

**事件綁定**(對應 Gradio 的 `.click`/`.submit`)就是原生 JS 的 `addEventListener`:
```javascript
$("#send").addEventListener("click", send);                 // 送出鈕
$("#msg").addEventListener("keydown", e => { if (e.key === "Enter") send(); });  // Enter 送出
$("#mic").addEventListener("click", toggleMic);             // 麥克風
```

## 5. 一次「送出」的完整資料流(跨越兩端)

```
瀏覽器:玩家打字、按送出 / Enter
   │  send():收集 {thread_id, text, voice_emotion}
   ▼  fetch("/api/say", POST, JSON)  ── HTTP ──▶
伺服器 server.py:api_say(req)
   sess = _get_session(req.thread_id)         # 取/還原 session(已結束→404)
   payload = {"player_input": req.text, ...}
   result = GRAPH.invoke(payload, {thread_id}) ← 進入後端的圖(第 5、6 課)
        └ customer_brain → apply_state → classify_ending → …
   組 resp(JSON):ai_reply / anger / turn / ended / (結束時 report)
   if ended: storage.save_game(...)            # 存歷史
   ◀── HTTP(JSON)──
瀏覽器:send() 拿到 d
   addMessage("奧客", d.ai_reply)  updateMeter(d.anger)  setOkekeFace(...)
   if d.ended: finishCustomer(d)  # 出報告、鎖輸入、下一位/班次總結
```

**前端只負責「fetch + 顯示」,FastAPI 只負責「轉接」,遊戲邏輯完全在後端的圖裡。** 三層各司其職。

## 6. 三個關鍵技術點(答辯常問)

1. **thread_id 怎麼讓多回合接起來**
   `/api/start` 時後端 `uuid` 產生 thread_id 回傳給前端,前端存在 `STATE.thread`。之後每次 `/api/say` 都帶同一個 thread_id,後端 `GRAPH.invoke` 用它讓 checkpointer **自動載回上次的 state**(憤怒值、歷史)。換 thread_id = 新遊戲。(Gradio 是 thread_id 存 `gr.State`,前端產生;web/ 改由後端產生回傳——但作用一樣。)

2. **第一回合 vs 後續**
   首回合 `payload = {**sess["init"], "player_input": text}`(送整包開局 state 初始化);之後 `SESSIONS[...].first = False`,只送 `{"player_input": text}`,其餘靠 checkpointer 接續。跟 `run_demo.py`、Gradio 版同邏輯。

3. **後端完全沒改 ⭐(這次換前端正好證明了它)**
   `graph/`、`services/`、`scenarios/`、`storage.py` 一行都沒動。從 Gradio 換到自訂網頁,只是把「直接呼叫 `GRAPH.invoke`」改成「`fetch` → FastAPI → `GRAPH.invoke`」,外面多一層 API 殼。**這就是當初把邏輯放後端、跟前端解耦的回報**——前端可以隨便換,後端不動如山。

## 7. 對照組:Gradio(`app.py`)是另一種「更單純的 in-process 做法」

`app.py` 還在,當**備援/對照組**(port 7860)。它示範了「不架 HTTP API」的最單純寫法:

```python
# 啟動:同樣只建一次圖
GRAPH = build_graph(SqliteSaver(_conn))

# session:用 gr.State(每個瀏覽器分頁各一份)
st_sid = gr.State(None); st_init = gr.State(None); st_first = gr.State(True); …

# handler:直接呼叫後端,不經 HTTP
def player_say(text, chat, sid, init, first, done, ...):
    payload = {**init, "player_input": text} if first else {"player_input": text}
    result = GRAPH.invoke(payload, {"configurable": {"thread_id": sid}})  # ← 直接呼叫!
    ...

# 事件綁定:Gradio 的 .click / .submit
send_btn.click(player_say, inputs=_say_inputs, outputs=_say_outputs)
textbox.submit(player_say, inputs=_say_inputs, outputs=_say_outputs)
```

**和 web/ 的對照重點:**

| 面向 | web/(主力) | Gradio app.py(備援) |
|---|---|---|
| 前後端關係 | 兩端,**HTTP/JSON** 溝通 | 同程式,**直接呼叫**(in-process) |
| 前端語言 | 任何能 `fetch` 的(這裡是原生 JS) | 綁死 Python(Gradio) |
| session 存哪 | 後端記憶體 `SESSIONS` + checkpointer | `gr.State`(前端各分頁一份) |
| thread_id 誰產生 | 後端 `/api/start` 回傳 | 前端 handler 內 `uuid` |
| 事件綁定 | `addEventListener` | `.click` / `.submit` |
| **後端的圖** | **完全相同** | **完全相同** |

> Gradio 的代價是**綁死 Python 前端**;好處是**最少程式碼、不必寫 API**。因為這個專案要做自訂的視覺(AKARU 式選關、立繪、音樂、語音),才升級成 web/ 那套。**選哪套,看你需不需要自訂前端。**

## 🎓 老師可能問

**Q:你的(主力)前端怎麼跟後端溝通?**
A:主力前端是原生 HTML/CSS/JS,跑在瀏覽器、不是 Python,沒辦法直接 import 後端,所以中間用 **FastAPI 包了一層 JSON API**。前端用 `fetch` 打 `/api/scenarios`(列關卡)、`/api/start`(開局)、`/api/say`(跑一回合),後端在伺服器這邊呼叫 `GRAPH.invoke` 再把結果以 JSON 回傳。同一個 8000 port 既送靜態網頁、又送 API。

**Q:那 thread_id 怎麼接續多回合?**
A:`/api/start` 時後端用 `uuid` 產生 thread_id 回傳,前端存在 JS 的 `STATE.thread`,之後每次 `/api/say` 都帶上。後端 `GRAPH.invoke` 用它讓 SqliteSaver checkpointer 自動載回上次 state。每場一個 thread_id,所以多人同時玩不會混。

**Q:`SESSIONS` 這個記憶體 dict 是做什麼的?伺服器重啟不就丟了?**
A:`SESSIONS` 只記殼層資訊(首回合與否、關卡、班次、活動時間);真正的 graph state 由 checkpointer 持久化在 `game_state.db`。所以伺服器重啟把 `SESSIONS` 清空也沒關係——`_get_session` 會從 checkpointer **還原**進行中的對局(只要跑過至少一回合),以 `first=False` 接著玩。

**Q:對局結束後玩家手殘連點送出,會怎樣?**
A:會被擋。結束時 `SESSIONS.pop` 清掉記憶體 session,但 checkpointer 永久保留那場 state。`_get_session` 一看 graph state 的 `ended=True` 就回 `None` → `/api/say` 直接回 **404「工作階段已結束」**。如果不擋,就會再跑一次 graph、**又花一次評審 LLM 的額度,還會覆寫汙染歷史紀錄**。

**Q:你之前不是用 Gradio?換成自訂網頁,後端改了多少?**
A:`graph/`、`services/`、`scenarios/`、`storage.py` **一行都沒改**。只是把「Gradio 直接呼叫 `GRAPH.invoke`」換成「前端 `fetch` → FastAPI → `GRAPH.invoke`」,外面多一層 API 殼。`app.py` 還留著當對照/備援(7860)。**這正好證明了把邏輯放後端、跟前端解耦的好處**——前端隨便換,後端不動。

**Q:為什麼不乾脆都用 Gradio 就好?**
A:Gradio 最單純(同程式、不用寫 API),但**綁死 Python 前端**,做不出我們要的自訂視覺(AKARU 橫向選關、立繪換臉、寶可夢音樂、語音輸入)。所以升級成 FastAPI + 原生 JS,代價是多寫一層 API,換來前端完全自由。
