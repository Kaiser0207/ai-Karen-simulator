## 1. 串流式 UI:為什麼 handler 要用 `yield`?

### 問題
最初 `player_say` 是「**一次做完才 `return`**」——它在同一次呼叫裡跑完 LLM(結束時還含評審)才回傳一次。結果:
- 你打的字不會先出現,要等奧客回完才一起跳出。
- 結束時結局台詞和報告同時出現。

### 解法:把 handler 改成 Python generator(用 `yield` 分階段)
Gradio 原生支援 generator handler:**每 `yield` 一次,前端就即時更新一次**。

```python
def player_say(text, chat, ...):
    # ① 先 yield:顯示玩家的話 + 「思考中」,並鎖輸入
    yield (thinking, ...)
    # ② 呼叫後端(這步在等 Gemini)
    result = GRAPH.invoke(...)
    # ③ yield:顯示奧客回應
    yield (after_reply, ...)
    # ④(結束時)先 yield 結局台詞 → 再 yield 報告
    yield (after_ending, ...)   # 結局先
    yield (..., report, ...)    # 報告後
```

效果:**玩家輸入立刻回饋 → 思考中 → 奧客回應 →(結束)結局 → 報告**,一步步出現,不再全擠在最後。

> 🔑 心法:**凡是中間有等待(尤其 LLM)的流程,用 `yield` 分段回饋**,先把使用者的動作顯示出來,體驗差很多。

## 2. 對話存檔:storage.py

遊戲結束時(在 `player_say` 第 ④ 步前)呼叫 `storage.save_game(...)`,把整場存成 `logs/{thread_id}.json`:

```python
storage.save_game(
    thread_id=sid, scenario=init["scenario"], ending_type=result["ending_type"],
    anger_history=new_anger_hist,      # 每回合憤怒值(含開局)
    emotion_history=new_emotion_hist,  # 每回合奧客情緒
    transcript=after_ending,           # 完整對話 [{"role","content"}, ...]
    report=result["report"],           # 評審報告
)
```

### 兩個累積的歷史是怎麼來的?
`anger_history` / `emotion_history` 不在後端 state 裡(後端只存「當前」憤怒值),而是**前端用 `gr.State` 逐回合累積**:
- `start_game`:`anger_hist=[初始值]`、`emotion_hist=[]`
- 每回合 `player_say`:`new_anger_hist = anger_hist + [result["anger"]]`,情緒同理。

> 為什麼放前端累積、不放後端?保持 LangGraph 節點是**純函式**(只關心當前回合),「歷史軌跡」這種展示用資料由應用層收集。時間戳也一樣由 storage 在寫檔當下產生。

### storage.py 三個函式
- `save_game(...)`:寫一場存檔。
- `list_games()`:列出所有場次摘要(給歷史下拉),最新在前。
- `load_game(thread_id)`:讀回完整一場。

## 3. 歷史紀錄頁

用 `gr.Tabs` 把介面分成「🎮 遊戲」「📜 歷史紀錄」兩頁。歷史頁:
- **下拉選單**(`_history_choices()`):列出過去每場(角色｜結局｜回合｜時間)。
- 選一場 → `view_game(thread_id)` 回傳三樣:
  - **對話回放**(Chatbot 顯示 transcript)
  - **憤怒值/情緒軌跡折線圖**(`trajectory_fig`:憤怒值折線 + 每點標註情緒)
  - **報告 + 情緒變化序列**(Markdown)

事件綁定:
```python
refresh_btn.click(refresh_history, outputs=[history_dd])     # 手動刷新
history_tab.select(refresh_history, outputs=[history_dd])    # 切到該頁自動刷新
history_dd.change(view_game, inputs=[history_dd], outputs=[hist_chatbot, hist_plot, hist_md])
```

> 注意 `history_tab.select(...)`:切換到歷史頁時自動重新整理清單,這樣剛玩完的新對局立刻出現。

## 4. 語音輸入(STT):services/stt.py

### 流程:語音不進後端的圖
```
麥克風錄音 → stt.transcribe(音檔) → 文字 → 走和打字完全一樣的 player_say 流程
```
STT 是**輸入轉接器**,套在 `graph.invoke` 之前;後端的圖完全不知道有語音這回事(第 7 課的解耦原則)。

### app.py 怎麼接
```python
mic = gr.Audio(sources=["microphone"], type="filepath", ...)

def on_record(audio_path, chat, ...):
    text = stt.transcribe(audio_path)        # 語音 → 文字
    if not text.strip():
        gr.Warning("沒聽清楚,請再說一次。"); yield (...); return
    for step in player_say(text, chat, ...):  # 沿用打字的回合流程
        yield (*step, None)                   # 末尾 None = 錄完自動清空錄音框

mic.stop_recording(on_record, inputs=..., outputs=_say_outputs + [mic])
```

### services/stt.py 重點
- 用 **faster-whisper**(Whisper 的高效實作)。
- 模型 **lazy + singleton**:只在第一次用到時載入一次。
- 輸出用 **opencc** 轉繁體(`s2twp`)。
- 都用「函式內才 import」的延後載入,**沒用語音時不佔資源**。

## 5. GPU 加速與「啟動預載」

### CUDA 函式庫的坑
faster-whisper 在 GPU 上靠 ctranslate2,需要 `libcublas.so.12`、cuDNN 等**運算函式庫**(系統只有顯卡驅動還不夠)。
解法(完全隔離):把 `nvidia-cublas-cu12`/`nvidia-cudnn-cu12` 裝進 **venv**,並在 `stt.py` 用 `ctypes` 以 `RTLD_GLOBAL` **預載**這些 `.so`——不必設 `LD_LIBRARY_PATH`、不碰系統。

### 啟動就掛上 GPU(warmup)
原本是「第一次錄音才載入」→ 第一句很卡。改成:
```python
# app.py 啟動時,用背景執行緒預載(不擋網頁)
if config.STT_WARMUP:
    threading.Thread(target=stt.warmup, daemon=True).start()
```
`warmup()` 載入模型 + 跑一次空音訊(連 CUDA kernel 都初始化)。網頁立刻開,whisper 在背景掛上 GPU,第一次錄音就不卡。可用 `.env` 的 `STT_WARMUP=0` 關閉(不用語音時不佔顯存)。

## 🎓 老師可能問

**Q:你的網頁怎麼做到打字立刻顯示、結局和報告分開出現?**
A:把事件處理函式寫成 Python generator,用 `yield` 分階段更新——先 yield 玩家訊息+思考中,再 yield 奧客回應,結束時先 yield 結局台詞、最後才 yield 報告。Gradio 會把每個 yield 即時推到前端。

**Q:對話紀錄存哪、存什麼?**
A:遊戲結束存成 `logs/{thread_id}.json`,含對話逐句、奧客情緒變化、憤怒值軌跡、結局、評審報告、時間戳。歷史頁讀這些檔做回放與折線圖。

**Q:語音輸入怎麼整合?會不會動到後端?**
A:用 faster-whisper 把麥克風音檔轉文字,在 `graph.invoke` 之前做掉,轉出的文字走和打字一樣的流程。後端的圖完全沒改——STT 只是輸入轉接器。

**Q:為什麼第一次錄音不卡?**
A:網頁啟動時用背景執行緒預載 whisper 到 GPU 並暖機,把「載入延遲」從使用者第一次錄音移到啟動階段,且不阻塞網頁開啟。
