## 1. 串流式即時回饋:web/ 怎麼做(不是 Gradio 的 yield)

### 問題
若「一次做完才回一次」——你打的字不會先出現,要等奧客回完、連結局與報告都算完才一起跳出,體驗很差。

### 解法:前端 `fetch` + 逐步更新 DOM
`web/` 不是 Gradio,**沒有 generator handler / `yield`**。即時回饋改由**前端 JavaScript** 負責:

1. 玩家送出 → 前端**先**把玩家的泡泡與「思考中」插進對話區(`app.js` 的 `send()`),鎖住輸入。
2. `fetch` 呼叫一次 `POST /api/say`(後端跑完一整個回合的圖才回傳一個 JSON)。
3. 收到回應 → 前端把「思考中」換成奧客回應、更新怒氣條/回合數/立繪表情(`updateMeter`、`setOkekeFace`)。
4. 若 `ended` → 前端再依結局台詞、評審報告分別渲染對應區塊。

> 🔑 心法:Gradio 用後端 `yield` 推進畫面;`web/` 把「分階段更新」搬到**前端 DOM 操作**。後端 `/api/say` 仍是「一個回合一次請求/一次回應」,即時感由前端在請求前後各更新一次畫面達成。

> 重點放在後面三塊(STT/SER/存檔/班次),這塊知道「即時感在前端做」即可。

## 2. 語音輸入(STT):瀏覽器 MediaRecorder → /api/stt → faster-whisper

### 流程:語音不進後端的圖
```
瀏覽器 MediaRecorder 錄音(webm/opus)
  → POST /api/stt(後端 faster-whisper 轉繁中文字)
  → 文字填進輸入框 → 走和打字完全一樣的 /api/say 流程
```
STT 是**輸入轉接器**,套在 `graph.invoke`(`/api/say`)之前;**後端的圖完全沒改**,不知道有語音這回事(學習 7 的解耦原則)。把 Gradio 的 `gr.Audio` 換成瀏覽器原生 `MediaRecorder`,後端轉接邏輯不變。

### 前端怎麼錄音(web/static/app.js)
不是 Gradio 的 `gr.Audio`,而是瀏覽器原生 API:
```js
// toggleMic():按一下開始錄、再按一下停
const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
mediaRec = new MediaRecorder(stream);
mediaRec.ondataavailable = (e) => { if (e.data?.size) recChunks.push(e.data); };
mediaRec.onstop = async () => {
  const blob = new Blob(recChunks, { type: mediaRec.mimeType || "audio/webm" });
  const fd = new FormData(); fd.append("audio", blob, "rec.webm");
  const d = await api("/api/stt", { method: "POST", body: fd, timeoutMs: 60000 });
  input.value += d.text;                 // 辨識文字填進輸入框
  STATE.voiceEmotion = d.emotion || null; // ← SER 結果(見第 3 節)
  if (VOICE.auto) send();                // 自動模式辨識完直接送;手動模式留給你檢查
};
```
另外前端還做了兩件貼心事(知道即可):
- **靜音自動送出**(`startSilenceMonitor`):用 Web Audio 量 RMS 音量,說話後若靜音超過設定秒數就自動 `stop()`(等同 Gradio 的「錄完自動處理」)。
- **逾時保護**:`api()` 內建 `AbortController`,STT 卡住不會永遠停在「辨識中…」。

### 後端 /api/stt(web/server.py)
```python
@app.post("/api/stt")
async def api_stt(audio: UploadFile = File(...)):
    data = await audio.read()                 # 收瀏覽器上傳的 webm/opus
    # 寫成暫存檔 → 丟給 faster-whisper;run_in_threadpool 不擋事件迴圈
    text, words, audio16 = await run_in_threadpool(stt.transcribe_full, tmp.name)
    resp = {"text": text}
    # 順手做 SER(best-effort,見第 3 節)
    ...
    return resp
```
重點:`transcribe_full` 一次回傳 **(text, words, audio16)**——文字、詞級時間戳、以及**解好碼的 16k 波形**。這個波形直接餵 SER,**SER 端不必再解一次 webm**。

### services/stt.py 重點(技術點仍正確,沿用到 web/)
- 用 **faster-whisper**(Whisper 的高效實作),模型 **lazy + singleton**:第一次用到才載入、且只載一次。
- 本機設定:`STT_MODEL=medium`、`STT_DEVICE=cuda`、`STT_COMPUTE=float16`(RTX 3090)。
- 輸出用 **opencc**(`s2twp`)轉繁體台灣用語;不可用則原樣回傳。
- `initial_prompt` 餵一句含標點的中文 → 引導 Whisper 補出標點(medium 常漏標點);`vad_filter` 去靜音、減幻聽。
- 都用「函式內才 import」的延後載入,**沒用語音時不佔資源**。

## 3. 🌟 語音情緒辨識(SER):辨玩家「怎麼說」(本專案多模態亮點)

> 這是評分亮點:STT 只在乎「**說了什麼**(內容/字面)」,SER 在乎「**怎麼說**(語氣/口吻)」。同一句「我幫你處理」,口氣火大 vs. 溫和有耐心,奧客的反應完全不同。

### 它解決什麼?
讓奧客不只看店員打的字,還「聽得出」店員的語氣——把語音當成**內容判斷之上的修正**,使奧客的反應更擬真、更有變化。

### 走外部 CRAB 微服務(services/ser_client.py)
SER 不是塞在主程式裡,而是**呼叫一支獨立的外部微服務(CRAB,預設 `port 8100`,由 `config.SER_URL` 指定)**:
```python
# services/ser_client.py —— 只用標準庫(urllib + json + base64),不新增依賴
def voice_emotion(audio_16k, text="", words=None):
    url = (config.SER_URL or "").strip()
    if not url or audio_16k is None or not len(audio_16k):
        return None
    try:
        # 把 16k float 波形轉成 16-bit PCM(int16)再 base64,送給微服務
        pcm = (np.clip(audio_16k, -1, 1) * 32767).astype("<i2").tobytes()
        body = json.dumps({"pcm_b64": base64.b64encode(pcm).decode(),
                           "sr": 16000, "text": text, "words": words}).encode()
        req = urllib.request.Request(url.rstrip("/") + "/predict_pcm", data=body,
                                     headers={"Content-Type": "application/json"})
        with urllib.request.urlopen(req, timeout=config.SER_TIMEOUT) as r:
            return json.loads(r.read().decode())   # {label, confidence, probs, ...}
    except Exception:        # 服務沒開 / 逾時 / 任何錯
        return None          # ← 一律回 None,絕不擋主流程
```
幾個設計重點:
- **送 16k 單聲道 int16 PCM**:遊戲已用 faster-whisper 解好碼(`audio16`),所以微服務端**不必再解 webm**;長語句還附 `words`(詞級時間戳)讓對方依時間戳切段加權。
- **辨 4 類語氣**:`Angry / Anxious / Happy / Neutral`。
- **只用標準庫(urllib)**:不為了 SER 多裝依賴。
- **best-effort(最重要)**:服務沒開、逾時、格式不符、任何例外 → **一律回 `None`**。`/api/stt` 的純文字照常回、`/api/say` 照常跑——**SER 是加分項,絕不能擋住主流程**。

### /api/stt 怎麼接 SER(web/server.py)
```python
resp = {"text": text}
# best-effort:有設 SER_URL、有文字、有波形才問;失敗就略過
if config.SER_URL and text and audio16 is not None:
    emo = await run_in_threadpool(ser_client.voice_emotion, audio16, text, words)
    if emo and emo.get("label"):
        resp["emotion"] = emo["label"]            # ← 前端拿去顯示 + 帶進 /api/say
        resp["emotion_probs"] = emo.get("probs")
return resp
```
前端收到後:在輸入框上方/泡泡下顯示語氣標籤給玩家看(`TONE_LABEL`、`attachTone`),並把 `d.emotion` 記在 `STATE.voiceEmotion`,送 `/api/say` 時一起帶上。

### voice_emotion 如何影響奧客(services/llm.py 的 _VOICE_TONE_RULE)
`/api/say` 把玩家語氣當 `voice_emotion` 帶進圖(`SayReq.voice_emotion` → `GameState.voice_emotion` → `customer_brain` 節點 → `llm.customer_turn`)。奧客大腦依語氣做兩件事(`_VOICE_TONE_RULE` 每條都含這兩部分):

| 語氣 | ① 情緒(調 `anger_change`) | ② 反應方式(調回話口吻/策略) |
|---|---|---|
| **Angry** | 覺得店員口氣差、沒誠意 → 安撫效果砍半,甚至由負轉正小漲 | 回嗆態度本身、拿服務態度反將、要求換人/叫主管 |
| **Anxious** | 嗅到店員心虛 → 安撫降幅縮小,別太快消氣 | 得寸進尺、加碼施壓:「你做得了主嗎?是不是新來的?」 |
| **Happy** | 感受到善意 → 火氣消一些;用詞也得體則加成 | 口氣軟下來但保留懷疑,半信半疑試探、提個小條件 |
| **Neutral** | 不額外加減 `anger_change` | 聚焦店員講的「內容」有沒有真的解決問題 |

關鍵:語氣**不只改 `anger_change` 的數字,還改變奧客「怎麼回話」的口吻與策略**——同樣內容、語氣不同,奧客反應就該明顯不一樣,避免每次都同一套句型。`anger_change` 接著進 `apply_state` 節點被夾限(`-30~30`)、再依難度的 `calm_resistance` 縮放安撫效果。打字回合 `voice_emotion=None`,`_voice_note` 回 `None` → 完全不影響,行為等同沒有 SER。

## 4. 對話存檔:storage.py(班次合檔的新版結構)

遊戲結束時(`/api/say` 判定 `ended`),`web/server.py` 從 graph messages 重建逐句對話,呼叫 `storage.save_game(...)` 落地:
```python
storage.save_game(
    thread_id=req.thread_id, scenario=sess["scenario"], ending_type=resp["ending_type"],
    anger_history=anger_history,       # 每回合憤怒值(含開局值)
    emotion_history=emotion_history,   # 每回合奧客情緒
    transcript=transcript,             # 完整對話 [{"role","content"}, ...]
    report=report,                     # 評審報告
    shift_id=sess.get("shift_id"),     # ← 班次資訊(第 5 節)
    shift_index=sess.get("shift_index"),
    shift_total=sess.get("shift_total"),
)
```

### 📌 存檔結構改版:從「一場一檔」改成「一班次一檔」
早期是「**一場一檔** `logs/{thread_id}.json`」。**現在改成**:

- **班次檔**:同一個 `shift_id` 的好幾關**合成一個檔** `logs/shift_<shift_id>.json`,裡面用 **`rounds[]` 陣列**裝各關(依 `shift_index` 排序),外層帶 `shift_id` / `shift_total` / 起訖時間(`created_at`、`updated_at`)。
- **單場檔**:沒有 `shift_id`(單人模式)的關 → `logs/solo/<thread_id>.json`,內容就是那一關紀錄本身。

每一關(round)仍含:對話逐句、奧客情緒變化、憤怒值軌跡、結局、評審報告、時間戳;另多了 `scenario_id`、`difficulty`、`char`(立繪)、`shift_*` 等欄位。**時間戳仍在這層(應用層)產生,不放進 LangGraph 節點**(保持節點純函式)。

`save_game` 寫班次檔時的細節:讀舊檔 → 同 `thread_id` 視為重存(先剔除再加,避免重複)→ 依 `shift_index` 排序 → 回寫,所以同一班次重玩某關不會留下殘檔。

### 三個對外函式(介面不變,前端不用改)
- `save_game(...)`:落地一關,**自動併進對應班次檔 / 寫成單場檔**。
- `list_games()`:列出**每關一筆**摘要(最新在前)。班次檔會被**攤平**成多筆(每個 round 一筆),前端歷史頁再依 `shift_id` 重新分組。
- `load_game(thread_id)`:掃所有檔(班次檔的 `rounds[]` 也掃),依 `thread_id` 取回**單一關**的完整紀錄。

> 內部用 `_iter_rounds(doc)` 統一處理:檔是「班次檔(有 `rounds[]`)」就攤成多筆,是「單場檔(單一 round)」就當一筆——也相容尚未遷移的舊式散檔。

## 5. 班次模式(shift):一次串多位客人

「班次」= 選一個難度,**連續服務同難度的多位客人**,最後給一份**班次總報告**(各客人分數平均)。

- **前端發起**(`app.js` 的 `startShift` / `startCustomer`):同一班次共用一個 `shift_id`,每位客人帶 `shift_index`、`shift_total` 呼叫 `/api/start`。
- **後端傳遞**(`web/server.py`):`StartReq` 收下 `shift_id/shift_index/shift_total` → 記在 session → 結束存檔時交給 `storage.save_game`,於是同班次的關都寫進**同一個** `logs/shift_<id>.json`。
- **歷史頁聚成一組**:`GET /api/history` 回攤平後的每關摘要,前端 `loadHistory()` 再**依 `shift_id` 分組**(沒有 `shift_id` 的舊紀錄各自成一組),一個班次顯示成一張可展開的卡片(標題=難度班次、副標=和解幾位、右側=班次平均分);展開後每關一列,點進去 `viewHistory(thread_id)` 看那關的回放+報告。

> 換句話說:存檔層用 `shift_id` 把同班次合檔,`list_games()` 攤平給通用 API,前端再用同一個 `shift_id` 把它們聚回一組顯示——存與顯示前後呼應。

## 6. GPU 加速與「啟動預載」(STT 用,技術點不變)

### CUDA 函式庫的坑
faster-whisper 在 GPU 上靠 ctranslate2,需要 `libcublas.so.12`、cuDNN 等**運算函式庫**(系統只有顯卡驅動還不夠)。
解法(完全隔離):把 `nvidia-cublas-cu12` / `nvidia-cudnn-cu12` 裝進 **venv**,在 `stt.py` 用 `ctypes` 以 `RTLD_GLOBAL` **預載**這些 `.so`(`_preload_cuda_libs()`,還做多輪載入處理相依順序)——不必設 `LD_LIBRARY_PATH`、不碰系統。

### 啟動就掛上 GPU(warmup)
原本是「第一次錄音才載入」→ 第一句很卡。改成在 `web/server.py` 啟動時用背景執行緒預載(不擋網頁啟動):
```python
# web/server.py
if config.STT_WARMUP:
    threading.Thread(target=stt.warmup, daemon=True).start()
```
`warmup()` 載入模型 + 跑一次空音訊(連 CUDA kernel 都初始化)。網頁立刻開,whisper 在背景掛上 GPU,**第一次錄音就不卡**。可用 `.env` 的 `STT_WARMUP=0` 關閉(不用語音時不佔顯存)。

## 🎓 老師可能問

**Q:你的網頁是 Gradio 嗎?即時回饋怎麼做?**
A:不是,主前端是 `web/`(FastAPI 薄層 + 原生 JS)。Gradio 是用後端 `yield` 分階段推畫面;我改成**前端 JavaScript** 做:送出前先把玩家泡泡+「思考中」插進 DOM,`fetch /api/say` 拿到回應後再換成奧客回應、更新怒氣條與立繪。即時感搬到前端,後端 `/api/say` 仍是一回合一次請求。

**Q:語音輸入怎麼整合?會不會動到後端的圖?**
A:瀏覽器用 `MediaRecorder` 錄成 webm,POST 到 `/api/stt`,後端用 faster-whisper(medium、GPU、ctypes 預載 CUDA、opencc 轉繁)轉成文字,文字走和打字一樣的 `/api/say`。圖完全沒改——STT 只是「圖之前的輸入轉接器」,只是把 Gradio 的 `gr.Audio` 換成瀏覽器原生錄音。

**Q:SER 語音情緒辨識是什麼?是你的多模態亮點嗎?**
A:是。STT 管「說了什麼」,SER 管「怎麼說」——辨玩家語氣分 Angry/Anxious/Happy/Neutral 四類。它走一支**外部 CRAB 微服務(port 8100)**,`ser_client.py` 只用標準庫 urllib 送 16k PCM 過去;結果當 `voice_emotion` 帶進 `/api/say`,影響奧客的 `anger_change` 與回話口吻(`_VOICE_TONE_RULE`)。重點是它**完全 best-effort**:服務沒開/逾時/失敗一律回 `None`,純文字照常跑,絕不擋主流程。

**Q:同一句話、語氣不同,奧客反應真的會不一樣嗎?**
A:會。`_VOICE_TONE_RULE` 每條語氣都含兩部分:① 調 `anger_change`(例如店員口氣兇 → 安撫效果砍半甚至轉漲);② 調反應方式(口氣兇 → 奧客回嗆態度、要求叫主管;緊張 → 奧客得寸進尺施壓)。所以語氣是「內容判斷之上的修正」,口吻與策略都會跟著變。

**Q:對話紀錄存哪、存什麼?班次怎麼分?**
A:結束時存進 `logs/`。**同一班次的幾關合成一個檔** `logs/shift_<shift_id>.json`(裡面 `rounds[]` 陣列,依 `shift_index` 排序);單人模式存 `logs/solo/<thread_id>.json`。每關含對話逐句、情緒變化、憤怒值軌跡、結局、評審報告、時間戳。`list_games()` 把班次檔攤平成每關一筆摘要,歷史頁再依 `shift_id` 把同班次聚回一張卡片顯示。

**Q:為什麼第一次錄音不卡?**
A:`web/server.py` 啟動時用背景執行緒預載 whisper 到 GPU 並暖機(跑一次空音訊初始化 CUDA kernel),把「載入延遲」從使用者第一次錄音移到啟動階段,且不阻塞網頁開啟。
