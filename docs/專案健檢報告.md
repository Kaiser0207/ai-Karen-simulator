# 專案健檢報告(AI 奧客應對演練)

> 產生日期:2026-06-10 · 基準 commit:`98e519b`(分支 testing)
> 範圍:後端(graph/services/storage/scenarios)、前端與 API(web/、app.py)、死碼與功能。
> 方法:三位審查員分頭實際讀碼 + grep/git 驗證,後端還在 mock 模式實跑狀態機驗證。
> **本報告只列問題、不含修改。** 每項標嚴重度與 `檔案:行號`,方便逐項處理。

## 總評
後端核心品質**明顯高於一般學生期末專題**:狀態機、reducer、checkpointer、失敗重試、結局優先序都正確且有測試覆蓋。真正要注意的集中在 **web/server.py 的「結束後重送 / 同 thread 並發」** 與 **「對外無認證」**,以及 **app.py(Gradio)與 web/ 兩套前端分歧** 造成的不一致與重複。

## 🔴 該優先修(高嚴重度)

### H1. 對局結束後再呼叫 `/api/say`,會把已完成的對局再跑一次 → 污染歷史 + 重複花 LLM 額度
- `web/server.py:211-264`(配合 `_get_session` 75-98)
- 結束時 session 在 `:264` 被 `SESSIONS.pop`,但若同一 `thread_id` 再來一個 `/api/say`(連點、網路重送、繞過前端守衛),`_get_session` 會從 checkpointer **還原**並再次 `GRAPH.invoke` → 又判一次結局、又跑一次 `judge`(多花一次 LLM)、又 `save_game` 覆寫同一筆歷史,`messages` 也被 reducer 再追加汙染。
- **修法方向**:server 端維持權威「已結束」狀態 —— `_get_session` 還原時讀 `vals.get("ended")`,已結束就讓 `/api/say` 直接回 409/400「本場已結束」,不再 invoke。

### H2. 同一 `thread_id` 並發 / 連點 → 一次輸入吃掉兩回合
- `web/server.py:205-223`;`_DB_LOCK` 只序列化 DB 讀寫(`:46-48`),不防同一 thread 兩個 `/api/say` 都被受理。
- 兩請求依序各跑「一個完整回合」→ 憤怒值套用兩次、`turn` +2。前端 `STATE.busy`(`app.js:491`)只是 client 端旗標,兩個分頁 / 直接打 API / 停用前快速雙擊都能繞過。
- **修法方向**:server 端對每個 `thread_id` 加「處理中」鎖,同 thread 有回合在跑時第二個請求回 409。

### H3. 所有 API 對外無認證、綁 `0.0.0.0`,`/api/history` 公開**所有人**的逐句對話
- `web/server.py:268-313`、`:328`(`host="0.0.0.0"`);`app.py:373` 同樣。
- `/api/history`、`/api/history/{thread_id}` 無驗證,回傳所有玩家完整對話、評審報告、時間戳。STT 端點無限流、無大小上限,可被濫用觸發昂貴的 whisper 推論。
- ⚠️ **與你 demo 用 ngrok 對外有直接關係**:通道開著時,拿到網址的人就能讀 `/api/history` 全部紀錄、消耗你的 Groq/Gemini 額度。
- **修法方向**:至少加一層簡單 token / Basic Auth;demo 只在需要時開通道、用完即關;`/api/history` 加分頁、(若多人)以班次/使用者隔離;STT 加大小上限與基本限流。

## 🟡 中嚴重度

### M1. 成本控制分(cost_control_score)在 Gradio 版不顯示,卻被算進歷史頁總分 → 兩邊分數對不上
- `graph/nodes.py:136` 產出第 4 面向;`storage.py:_report_score` 把它算進平均;但 `app.py`(radar_fig / report_md)只顯示 empathy/crisis/compliance 三項。web 版(`app.js:711-734`)有正確顯示 4 項。
- 後果:Gradio 當下報告(3 面向)與歷史頁分數(4 面向平均)不一致;玩家看不到「無腦讓步被扣的成本分」這個專題賣點。
- **修法方向**:app.py 補上 `cost_control_score`,與 storage 對齊;或直接降級 app.py(見 C1)。

### M2. `api_say` 結束分支直接索引 `result["report"]`、`result["messages"][-1]`,異常時冒裸 500
- `web/server.py:244-247`。正常流程 judge 一定有填,但若 graph 回傳不完整結構,會 `KeyError`/`IndexError` → 前端只看到「請求失敗」。
- **修法方向**:改 `result.get(...)` + 後備值,包一層轉成友善錯誤訊息。

### M3. 記憶體 session 回收只在「有新請求」時觸發,全員離線後不回收
- `web/server.py:68-73`,`_gc_sessions` 無背景定時器。長期掛機會緩慢累積過期 session(每筆含整個 init dict + scenario)。
- **修法方向**:加 daemon thread 定期清,或接受現狀但註解標明。

### M4. STT 上傳無大小上限 / 無 MIME 白名單
- `web/server.py:278-304`。`audio.read()` 無上限(大檔整包進記憶體);`suffix` 直接取自 `audio.filename`(只當暫存副檔名、無遍歷風險,但仍應限制)。
- **修法方向**:限制 `len(data)`(如 ≤25MB)、副檔名白名單 `.webm/.wav/.ogg/.mp3`。

### M5. 前端 `/api/stt` 的 `fetch` 沒有逾時 → STT 卡住時 UI 永久「辨識中…」
- `web/static/app.js:688`,唯獨 STT 上傳用裸 `fetch`、無 `AbortController`(其他都走 `api()` 帶 timeout)。後端慢/掛時麥克風被 disable、placeholder 卡住,只能重整頁面。
- **修法方向**:STT 也走 `api()` 或加 `AbortController` + 逾時,逾時後還原麥克風與提示。

### M6. app.py(Gradio)與 web 版邏輯分歧,且 Gradio 的 SQLite 無 `_DB_LOCK` 併發保護
- `app.py:31-32` 無鎖,Gradio 多執行緒下同一 cursor 易出 `database is locked`;且缺班次 / cost / 語音情緒 / SER。
- 兩套寫進**同一個 `logs/`**,但 app.py 存的紀錄缺 `shift_id/difficulty/char` → 在 web 歷史頁被當「solo / 無難度色」,歷史混雜。
- **修法方向**:明確凍結 app.py(見 C1),或補 `_DB_LOCK` 與欄位;否則停用 app.py 寫歷史以免污染。

## 🟢 低嚴重度 / 小細節

- **L1. mock 評審忽略「讓步成本」→ mock 與真實路徑不一致**(`services/llm.py:88-90`):`_mock_judge_report` 不吃 cost_spent/budget,「無腦全額退費」的 compliance 不會被懲罰(只有確定性的 cost_control_score 會)。題目要求 mock/real 一致 → 建議 mock 也依成本下修 compliance。
- **L2. 關卡 JSON 值無範圍驗證**(`scenarios/loader.py:31-40`):`_validate_scenario` 只檢查欄位存在,不檢查值。若 `max_turns=0` 會第一回合就 timeout、`initial_anger` 為字串會在 `apply_state` 丟 TypeError。目前 8 關值都正常,屬「驗證缺口」非現行 bug。建議驗 `initial_anger` 0~100 int、`max_turns` ≥1 int、`calm_resistance>0`。
- **L3. `_friendly_error`/`_is_transient` 用字串比對例外訊息**(`web/server.py:106-132`、`app.py:111-138`):含 "500"/"connection" 子字串會誤判為可重試。影響小(只重試 1 次)。建議用例外型別/狀態碼。
- **L4. `storage.list_games`/`load_game` 每次全量 `rglob` 讀檔**(`storage.py:118-151`):對局多時線性變慢,且 `/api/history` 無分頁。功能正確,純效能。
- **L5. `voice_emotion` 未在 server 端驗白名單**(`web/server.py:216`):來自 client 的任意字串會塞進 LLM 脈絡。實務上 `_VOICE_TONE_RULE.get()` 只認 4 個 key、未知回 None **無實害**,但建議用 `Literal["Angry","Happy","Neutral","Anxious"]` 顯式驗證。
- **L6. 前端 `escapeHtml` 只處理 `& < >`,未處理屬性脈絡**(`app.js:193`、`:814`):`char` 插入 `<img onerror=...>` 屬性值。目前 `char` 來自可信 scenario JSON **無實害**,屬防禦性建議(改用 `img.onerror = ()=>{}` 而非內聯字串)。
- **L7. `calm_resistance<1` 會「放大」安撫效果**(`graph/nodes.py:48-49`):easy 關 resistance=0.85/0.9,負向 delta 除以 <1 會更負。這其實是「簡單關更好安撫」的刻意設計,但**註解只寫困難關、沒寫簡單關放大** → 容易被後人當 bug 改掉。建議補註解,非 bug。
- **L8. 結局回合歷史回放出現兩則氣泡**:結局回合的「奧客本回合台詞」與「結局台詞」是兩個 AIMessage;即時 UI 會合併,但 web 存歷史是從 `result["messages"]` 重建 → 回放看到兩則,且與 app.py 存法不一致。屬顯示細節。

## 建議處理順序(我的推薦)
1. **先修 H1 + H2**(結束後重送、同 thread 並發)—— 影響歷史正確性與 LLM 花費,是最實際的 bug。
2. **demo 前處理 H3 的部署面**(用完關 ngrok、考慮加簡單 token / 綁 127.0.0.1)。
3. **決定 C1/M1/M6 的前端方向**(只留 web/ 還是維護 app.py)—— 一個決定解掉多項不一致與重複。
4. **挑 1~2 個 CP 值高的 feature**(F1 報告匯出、F2 SER 可視化)讓 demo 更亮眼。
5. 其餘 M/L 與 cleanup 有空再逐項清。
