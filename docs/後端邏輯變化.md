# 後端邏輯變化說明(不含前端)

> 記錄這一輪對**後端遊戲邏輯/服務層**的修改:改了什麼、為什麼、影響哪些檔與文件。
> 範圍只含後端(`graph/`、`services/`、`scenarios/`、`prompts/`、`tests/`),不含前端(Gradio / `web/`)。
> 對應測試:`tests/`(pytest);可 `OKEKE_USE_MOCK=1 uv run pytest` 全部驗證。

## 1. 🔴「成功」條件改變(最重要)

**改動位置**:`graph/nodes.py` 的 `classify_ending`。

**之前**:
```python
elif state["anger"] <= 0 or state["ended"]:   # 血條歸零「或」LLM 判和解 → 成功
    et = "success"
```
**之後**:
```python
elif state["ended"]:    # 只由 LLM(CustomerTurn.ended)判定「玩家提出完美方案、顧客願和解」
    et = "success"
```

**為什麼**:血條低**只代表顧客冷靜**,不等於「問題解決、願意和解」。把「成功」交給 LLM 判斷(它才知道玩家是否真的提出完美方案),更符合真實情境;憤怒值只負責「失敗(爆表)」與「氣氛」。

**結局優先級(維持此順序)**:
1. `fail` — `anger >= 100`(最優先,即使同回合 LLM 也說和解,爆表仍算砸店)
2. `success` — `ended is True`(LLM 判定)
3. `timeout` — `turn >= max_turns`(success 優先於 timeout:最後一回合談成也算成功)
4. `None` — 繼續

> 對應測試:`test_zero_anger_without_ended_is_NOT_success`(血條 0 但沒 ended → 不算成功)、`test_fail_beats_ended`、`test_success_beats_timeout`。
> **影響文件**:學習_5、學習_6、完整技術參考(成功條件原本寫「anger≤0 或 ended」,要改成「只看 ended」)。

## 2. 🔴 憤怒/情緒軌跡改由「後端」持久化

**改動**:`GameState` 新增兩個欄位(`graph/state.py`):
```python
anger_history:   Annotated[list, operator.add]  # 每回合結束後的憤怒值(含開局)
emotion_history: Annotated[list, operator.add]  # 每回合奧客情緒(長度=回合數)
```
- reducer 用 `operator.add` → 節點回傳 `[新值]` 時**自動串接**到舊 list(跟 `messages` 的 add_messages 同概念,但用在一般 list)。

**誰寫入**:
- `loader.load`:開局 `anger_history=[initial_anger]`、`emotion_history=[]`。
- `apply_state`:每回合回傳 `anger_history=[new_anger]`、`emotion_history=[emotion]` → 自動累積。

**為什麼**:之前軌跡是**前端**(Gradio 的 `gr.State`)累積的,伺服器重啟或換前端就沒了。改放進**後端 GameState** → 由 **checkpointer(SqliteSaver)持久化**,所以:
- **伺服器重啟可從 checkpointer 還原進行中的對局**(含軌跡)。
- 評審能直接從 state 拿到軌跡(見變更 3)。
- 不再依賴特定前端 —— `web/` 的 FastAPI 前端就靠這個。

> 對應測試:`test_histories_appended`。
> **影響文件**:學習_2(state 欄位)、學習_8(原本說「軌跡放前端 gr.State」要改為「後端 state、checkpointer 持久化」)。

## 3. 🟠 評審「結果感知」(outcome-aware)

**改動**:`services/llm.py` 與 `graph/nodes.py`、`prompts/judge_system.txt`。

- `judge` 節點現在把**結局與憤怒軌跡**一起傳給評審:
  ```python
  llm.judge_report(state["messages"],
                   ending_type=state["ending_type"],
                   anger_history=state.get("anger_history"),
                   max_turns=state["max_turns"])
  ```
- 新增 `_outcome_note(ending_type, anger_history, max_turns)`:組一段「【本場結果】結局…憤怒軌跡 50→72→…請依此校準分數,不得與結果矛盾」,當成額外的 system 訊息給評審。
- `prompts/judge_system.txt` 加了**校準規則 + 評分錨點**(失敗→empathy/crisis 偏低;成功才給高分;90+ 罕見…)。

**為什麼**:之前評審只看對話,容易出現「**顧客最後爆走,卻誇店員危機處理優秀**」的矛盾。把結果一起給它,分數就會呼應勝負、更合理。

> **影響文件**:學習_4(judge_report 簽名與行為)、LLM服務層詳解。

## 4. 🟠 結構化輸出:解析重試 + 後備

**改動**:`services/llm.py`。

- 新增 `_invoke_structured(model, msgs)`:LLM 回傳**格式不符 Pydantic schema** 時,**同 prompt 重抽最多 3 次**(`_STRUCT_ATTEMPTS`),退避遞增。
  - 注意分工:這跟**前端/web 層**的「暫時性錯誤(429)重試」不同——這裡專處理「**格式解析失敗**」。
- **後備(fallback)**:重試仍失敗時不讓流程崩潰:
  - 奧客大腦 `_real_customer_turn`:回**中性台詞**(`anger_change=0, ended=False`),遊戲可繼續。
  - 評審 `_real_judge_report`:退回 **mock 關鍵字報告**,確保**結束時一定有報告**,不會整場無結算。

**為什麼**:LLM 偶爾會吐不符 schema 的東西;重試通常就好,真的不行也要優雅降級,不能讓玩家卡死或拿不到報告。

> **影響文件**:學習_4、開發錯誤紀錄(可當一則 robustness 改進)。

---

## 5. 🟡 關卡載入即驗證

**改動**:`scenarios/loader.py` 新增 `_validate_scenario`,在 `load()` 時檢查必備欄位與三種 `ending_lines`,缺了就**明確報錯**(而非拖到遊戲中途才 `KeyError`)。
- `_REQUIRED_FIELDS = (scenario_id, name, genre, persona, situation, triggers, opening_line, initial_anger, max_turns)`
- `_REQUIRED_ENDINGS = (fail, success, timeout)`

**為什麼**:新增角色時打錯/漏欄位,能在載入當下就知道,而不是玩到一半崩潰。

> **影響文件**:學習_3(loader)。

---

## 6. 🟡 mock 評審也呼應勝負

**改動**:`_mock_judge_report(messages, ending_type)` 現在依結局校準:
- `fail` → empathy/crisis 上限壓低(≤50 / ≤45),加一條「情緒徹底爆走」評語。
- `timeout` → crisis ≤55,加「拖到回合用盡」評語。
- `summary` 也看是否 `success`。

**為什麼**:讓 **mock 模式**的報告也跟結局一致(對齊真實評審的 outcome-aware),demo 用 mock 時不會出現矛盾報告。

> 對應測試:`test_judge_calibrates_down_on_fail`。

---

## 7. 🟡 prompt 強化(行為更穩定)

- `prompts/customer_system.txt`:加了**`anger_change` 評分準則**(踩雷 +15~30、純拖時間 +5~12、同理 −5~12、具體方案 −15~25、同理+方案 −25~30)、**emotion 要與憤怒程度一致**、**範例**。→ 讓奧客給分尺度更一致、情緒更合理。
- `prompts/judge_system.txt`:加**結果校準規則 + 評分錨點**(見變更 3)。

> **影響文件**:LLM服務層詳解(prompt 內容)、學習_4。

---

## 8. 🟢 其他穩健性

- **模板快取**:`loader._load_template`(`_CUSTOMER_TEMPLATE`)、`llm._judge_system_prompt`(`_JUDGE_TEMPLATE`)只讀檔一次。
- **`set_ending` 防禦取台詞**:`ending_lines.get(ending_type) or "(對話結束。)"`,缺台詞不會 KeyError。
- **導入 `logging`**:後備觸發時 `logger.warning(...)` 留痕,方便排查。
