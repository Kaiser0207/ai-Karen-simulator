# AI 奧客應對演練 — 開發錯誤紀錄

> 本文件記錄開發過程中實際遇到的問題、原因、解法與啟示,供期末報告「踩到的雷」章節引用。
> 分兩部分:**設計階段**發現的邏輯問題(寫程式前就抓出)、**實作階段**遇到的實際錯誤。

---

## A. 設計階段發現的問題(寫 code 前就抓出並修正)

> 這些是在撰寫設計文件(v1.1 → v1.3)時,逐步推敲資料流發現的設計缺陷。能在動工前抓出,省下大量重寫成本。

### A-1. 開場白會讓奧客「第一回合失憶」
- **現象**:若只在前端顯示開場白,而沒放進對話歷史,LLM 第一回合看不到自己講過的開場白。
- **原因**:對話流程從 `customer_brain` 開始,但 `messages` 初始為空。
- **解法**:`loader.load()` 初始化 state 時就把開場白放進歷史:`messages = [AIMessage(opening_line)]`。
- **啟示**:LLM 的「記憶」完全來自傳入的 messages,任何要它記得的內容都必須在歷史裡。

### A-2. 結局台詞的生成時機自相矛盾
- **現象**:想讓 LLM 即時生成結局台詞,但失敗結局時,`customer_brain` 講話的當下「還不知道自己這回合會爆表」(憤怒值是下一個節點才更新),可能講出平淡台詞卻配上爆表血條。
- **原因**:台詞生成(customer_brain)早於憤怒值結算(apply_state)。
- **解法**:三種結局台詞**預寫在 scenario JSON**,由 `set_ending` 直接附加,保證台詞與血條一致,也省一次 LLM 呼叫。
- **啟示**:狀態機裡「事件發生順序」會影響語意,需釐清每個值在哪一步才確定。

### A-3. `system_prompt.format()` 會被大括號炸掉
- **現象**:用 `system_prompt.format(anger=...)` 注入憤怒值,一旦 prompt 內含 JSON 範例的 `{}`,就會丟 `KeyError`/`ValueError`。
- **解法**:不對整段 prompt 做 format;改用獨立的 system 訊息注入憤怒值;載入模板時用 `str.replace` 而非 `str.format`。
- **啟示**:含使用者內容/範例的字串,別用 `str.format`,改用 `replace` 或 `string.Template`。

### A-4. 結局類型無法透過 conditional edge 傳遞
- **現象**:原本想在 LangGraph 的岔路判斷函式裡決定結局類型,但 `set_ending` 讀不到。
- **原因**:**conditional edge 函式的回傳值只用來選邊,不會寫進 state**。
- **解法**:拆成兩步——`classify_ending`(節點,把 `ending_type` 寫進 state)+ `route_after_classify`(只讀 state 選邊)。
- **啟示**:LangGraph 中「要被後續節點使用的值」必須由節點寫入 state,不能依賴 edge 函式回傳值。

## B. 實作階段遇到的實際錯誤

### B-1. `uv init` 把子專案併入上層 workspace
- **現象**:在 `final_project` 執行 `uv init` 時出現
  `Adding okeke-drill as member of workspace /home/brant/Project`,
  子專案被自動加進上層 `/home/brant/Project` 的 workspace。
- **原因**:上層 `pyproject.toml` 已有 `[tool.uv.workspace]`,uv 會把新建子專案登記為成員,導致共用上層的 `.venv` 與 `uv.lock`,失去隔離。
- **解法**:
  1. 還原上層 `pyproject.toml` 的 `members`(移除 `final_project`)。
  2. 在 `final_project/pyproject.toml` 加上自己的 `[tool.uv.workspace]`,宣告為獨立 workspace 根目錄。
  - 結果:`.venv`、`uv.lock` 都落在 `final_project/` 內,完全自包含。
- **啟示**:在已是 uv workspace 的目錄底下建子專案,要主動宣告獨立,否則會被併入。

### B-2. 工作目錄重置,`uv add` 裝到錯誤的專案
- **現象**:執行 `uv add python-dotenv` 後,發現它改的是**上層** `/home/brant/Project/pyproject.toml`,套件也裝進上層 venv;`final_project` 反而沒裝到。
- **原因**:跨指令之間工作目錄被重置回 `/home/brant/Project`,uv 以當前目錄判定專案。
- **解法**:
  1. 用 `uv remove --project /home/brant/Project python-dotenv` 還原上層。
  2. 改用 `uv add --directory /home/brant/Project/final_project <pkg>` **明確指定目錄**。
- **啟示**:uv 指令對「當前工作目錄」敏感;批次操作時一律加 `--directory`/`--project` 指定目標,避免裝錯地方。

### B-3. mock 模式「失敗結局」測不出來
- **現象**:驗證腳本的失敗場跑完憤怒值停在 96,沒到 100,結局未觸發。
- **原因**:腳本台詞「這是公司規定,本來就沒辦法**免單**」中,「免單」剛好是 mock 的「解決方案」關鍵字,把官腔造成的 +22 抵銷掉了。
- **解法**:把該句改掉、移除「免單」等解方關鍵字,讓三句純官腔累加突破 100。
- **啟示**:用關鍵字規則模擬時,測試輸入要避免「無意間命中相反類別的關鍵字」;這也反映 mock 規則本身較粗糙(真 LLM 不會有此問題)。

### B-4. 覆寫既有檔案前需先讀取
- **現象**:`uv init` 產生的空 `README.md` 直接覆寫時,工具報錯
  `File has not been read yet. Read it first before writing to it.`
- **原因**:編輯工具要求覆寫既有檔案前必須先讀取該檔(避免誤蓋)。
- **解法**:先讀取再覆寫。
- **啟示**:屬工具保護機制,非程式錯誤;流程上「先讀再寫」。

### B-5. Gemini `gemini-2.0-flash` 回 429(免費額度為 0)
- **現象**:接上真實 Gemini 後,呼叫 `gemini-2.0-flash` 直接拋
  `ChatGoogleGenerativeAIError ... (RESOURCE_EXHAUSTED): 429`,
  訊息含 `limit: 0, model: gemini-2.0-flash`。
- **原因**:API key **有效**(認證通過),但此帳號/專案對 `gemini-2.0-flash` 的免費額度為 0,並非 key 失效。
- **解法**:寫一支探測腳本逐一試多個模型,發現 `gemini-2.5-flash` 可用,改 `.env` 的 `CUSTOMER_MODEL`/`JUDGE_MODEL` 為 `gemini-2.5-flash`,問題解決。
- **啟示**:
  - 429 不一定是「用太多」;`limit: 0` 表示該模型在此帳號**沒有免費額度**,換模型即可。
  - 區分「key 無效(401/403)」與「配額問題(429)」很重要,排錯方向完全不同。

### B-6.(注意事項)免費額度速率限制
- **現象**:Gemini 免費版有每分鐘/每日請求上限;一場遊戲每回合 1 次 + 結束評審 1 次,密集測試可能再次撞到 429。
- **對策**:測邏輯時切回 mock(`OKEKE_USE_MOCK=1`)省額度;或加上重試/退避;正式 demo 控制節奏。

### B-7.(安全提醒)API key 一度以明文出現
- **現象**:設定過程中 API key 以明文貼出。
- **對策**:`.env` 已被 `.gitignore` 忽略(不進 git);建議將曾外流的 key 於 AI Studio **重新產生(regenerate)**,舊 key 作廢。
- **啟示**:金鑰一律放 `.env` 並 gitignore;曾外流者立即輪替。

### B-8. Gradio 6 的 Chatbot 移除了 `type` 參數
- **現象**:做網頁介面(Phase 3)時,寫 `gr.Chatbot(type="messages")`,一啟動就報
  `TypeError: Chatbot.__init__() got an unexpected keyword argument 'type'`。
- **原因**:這是 **Gradio 大版本升級(我們裝的是 6.16)造成的 API 變動**。舊版需要用 `type="messages"` 指定對話格式,**新版把 messages(`{"role","content"}` 字典)格式變成預設且唯一**,於是 `type` 參數被移除了——舊範例的寫法在新版就會壞。
- **解法**:移除 `type="messages"`,直接 `gr.Chatbot(...)`;對話資料維持 `{"role","content"}` 字典格式即可正常運作。排查時用 `inspect.signature(gr.Chatbot.__init__)` 直接查新版接受哪些參數,最快。
- **啟示**:套件大版本升級常有破壞性 API 變動;遇到 `unexpected keyword argument` 別硬套舊範例,**直接查當前版本的函式簽名/官方文件**確認參數。

### B-9. 介面更新「全擠在最後出現」(玩家訊息、結局、報告沒有分階段)
- **現象**:網頁打字送出後——(1)**自己打的字不會先出現**,要等奧客回完才跟回應一起跳出;(2)遊戲結束時,**結局台詞和評審報告同時出現**,而非「先結局、再報告」。
- **原因**:事件處理函式 `player_say` 原本是「**一次做完才 `return`**」——它在同一次呼叫裡跑完 LLM(結束時還包含評審)才回傳一次,所以畫面只在最後更新一次,中間步驟看不到。
- **解法**:把 handler 改成 **Python generator,用 `yield` 分階段更新**:① 先 `yield` 顯示玩家訊息 +「思考中」並鎖輸入 → ② 呼叫後端 → ③ `yield` 奧客回應 → ④(結束時)`yield` 結局台詞 → ⑤ `yield` 評審報告。Gradio 原生支援 generator handler,會把每個 `yield` 即時推到前端。
- **啟示**:介面的「即時感/分階段回饋」要靠**串流(yield)**,別把多步驟塞進一次 `return`;尤其有 LLM 等待時,**先回饋使用者的輸入**能大幅改善體驗。

### B-10. 對話框出現雙層上下捲軸
- **現象**:`gr.Chatbot` 對話框看起來有兩條上下捲軸(巢狀捲動感)。
- **原因**:Chatbot 的外層容器與內層訊息區可能都套了 `overflow`,形成巢狀捲軸(Gradio 版面常見狀況)。
- **解法**:用 `elem_id` 標記 Chatbot,加自訂 CSS 讓外層不捲、只保留內層訊息區捲動。
- **啟示**:UI 細節(捲軸、版面)**無法只靠程式邏輯驗證,要實際在瀏覽器檢查**;CSS 針對框架內部結構時,選擇器可能隨 Gradio 版本變動而需微調。

### B-11. faster-whisper 用 GPU 報 `libcublas.so.12 is not found`
- **現象**:把 STT 設成 `device="cuda"`,模型載入沒事,但一開始轉錄就拋
  `RuntimeError: Library libcublas.so.12 is not found or cannot be loaded`。
- **原因**:faster-whisper 的後端 **ctranslate2 在 GPU 上需要 CUDA 運算函式庫(cuBLAS/cuDNN)**,但系統 driver(nvidia-smi 可用)只含驅動,不含這些 userspace 函式庫;pip 也沒自動帶。
- **解法(完全隔離,不碰系統)**:
  1. 把函式庫裝進 **專案 venv**:`uv add nvidia-cublas-cu12 nvidia-cudnn-cu12`。
  2. 在 `services/stt.py` 用 **ctypes 以 `RTLD_GLOBAL` 預載**這些 `.so`(從 venv 的 `nvidia/*/lib/` 找),這樣 ctranslate2 依 soname `dlopen` 時就會命中已載入的版本——**不必設 `LD_LIBRARY_PATH`、不改系統環境**。
  3. 注意 `nvidia` 是 **命名空間套件**,要用 `nvidia.__path__`(`__file__` 會是 `None`)。
- **啟示**:
  - GPU 推論常缺的是「CUDA 運算函式庫」,跟「有沒有顯卡/驅動」是兩回事。
  - 共用伺服器上,把 GPU 相依**裝進 venv + 程式內預載**,可在「用 GPU」與「不污染系統/不影響他人」之間取得平衡。

## C. 改進紀錄(非錯誤,屬優化)

> 這些不是 bug,而是開發過程中為了體驗/效能做的優化決策,一樣值得寫進報告。

### C-1. STT 模型改為「網頁啟動就預載到 GPU」
- **原本狀況**:`services/stt.py` 的模型是 **lazy 載入**——第一次有人錄音時才載入。導致**第一句語音很卡**(要等下載 + 載入 VRAM + 初始化 CUDA kernel)。
- **做法**:
  1. 新增 `warmup()`:載入模型 + 跑一次空音訊推論(連 CUDA kernel 也初始化好,不只載權重)。
  2. `app.py` 啟動時用 **背景執行緒(daemon thread)** 呼叫 `warmup()`——網頁立刻開得起來,whisper 在背景並行掛上 GPU。
  3. 加 `STT_WARMUP` 開關(`.env`),可關閉以「不用語音時不佔 GPU 顯存」。
- **效果**:第一次錄音不再卡;網頁啟動速度不受影響(背景載入,不擋 UI)。
- **取捨**:暖機後模型**常駐 GPU 約 1~2GB VRAM**(app 執行期間持續佔用)。共用伺服器若在意顯存,可設 `STT_WARMUP=0` 退回 lazy。
- **啟示**:有「首次使用很慢」的重資源(模型/連線),可在**啟動時用背景執行緒預熱**,把延遲從使用者操作當下移到啟動階段,且不阻塞 UI。

### C-2. 網頁加入錯誤處理與退避重試(避免 demo 當機)
- **原本狀況**:`player_say` 的 `GRAPH.invoke()` 和 `on_record` 的 `stt.transcribe()` 沒有 try/except。若 Gemini 回 **429(額度/速率)**、網路逾時,或 STT 轉錄失敗,例外會往外拋,**UI 卡在「思考中」、輸入鎖死,整場玩不下去**——demo 當下撞到很尷尬。
- **做法**:
  1. 包 try/except:出錯時用 `gr.Warning` 顯示**友善訊息**(依錯誤內容區分「達到使用上限」「連線逾時」等),並**解鎖輸入、把文字還回輸入框**讓玩家直接重送。
  2. 對**暫時性錯誤**(429/timeout/connection…)加**一次退避重試**(`_invoke_with_retry`,等 2 秒再試);非暫時性錯誤則立即回報。
  3. 重試/恢復時把 `first` 設 `False`:該回合輸入已被 checkpointer 記錄,重送不必重帶開局 state,避免開場白重複。
- **效果**:撞 429 或語音失敗時,遊戲**不會卡死**,玩家看到提示後可立即重試;demo 穩健度大幅提升。
- **啟示**:任何**會呼叫外部服務**(LLM API、模型推論)的地方都要假設它**會失敗**;前端要能優雅降級(提示 + 可重試),不要讓單次失敗鎖死整個流程。

## D. 小結:這些錯誤帶來的設計原則

1. **隔離環境**:子專案要明確宣告獨立 workspace,套件操作指定 `--directory`。
2. **狀態機資料流**:要被後續使用的值必須寫入 state;留意各值「在哪一步才確定」。
3. **字串處理**:含範例/使用者內容的字串避免 `str.format`。
4. **LLM 排錯**:分清 key 無效(401/403)與配額(429);429 看 `limit` 判斷是否該換模型。
5. **金鑰安全**:`.env` + gitignore,外流即輪替。
6. **雙模式開發**:mock 與真實 LLM 可切換,讓邏輯測試不依賴 key、不花額度。
7. **套件版本意識**:大版本升級常有破壞性 API 變動,遇到參數錯誤先查當前版本的簽名/文件,別照舊範例。
8. **介面用串流回饋**:有等待(LLM)的步驟,用 `yield` 分階段更新先回饋使用者;UI 細節要在瀏覽器實測,不能只靠邏輯驗證。
