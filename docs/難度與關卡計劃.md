# 難度分級與關卡擴充計劃

> 目標:把目前 2 關擴充成 6–8 關、跨情境,並加入「簡單／普通／困難」三階難度。
> 全程資料驅動(只動 `scenarios/*.json` + 少量前後端),不改遊戲核心邏輯。

---

## 1. 現況盤點

- 關卡 = `scenarios/*.json`,目前 2 個:
  - `zhang_dama`(餐飲・無理取鬧)initial_anger 50 / max_turns 8
  - `liu_dong`(零售・攀關係要折扣)initial_anger 40 / max_turns 8
- 每個 JSON 欄位:`scenario_id, name, genre, avatar, initial_anger, max_turns,
  tts_voice, persona, situation, triggers, opening_line, ending_lines{fail,success,timeout}`。
- 憤怒變化:LLM(奧客回合)輸出 `anger_change` → 後端夾限 `[-30, 30]` → 血條夾 `[0,100]`
  (`graph/nodes.py:apply_state`)。「脾氣好不好安撫」目前**只靠 persona 文字**引導。
- 結局:`anger>=100` fail → `ended` success → `turn>=max_turns` timeout。

---

## 2. 難度三階設計

用兩個既有欄位(`initial_anger` / `max_turns`)+ 一個**新欄位 `difficulty`** 表達:

| 難度 | difficulty | initial_anger | max_turns | 奧客脾氣(persona 引導) |
|------|-----------|---------------|-----------|----------------------|
| 簡單 ★    | `easy`   | 30 | 8 | 講道理、給台階就下;怒氣降得快 |
| 普通 ★★   | `normal` | 50 | 6 | 標準奧客;有理可談但會盧 |
| 困難 ★★★  | `hard`   | 70 | 5 | 硬頸、翻舊帳、容易再爆;怒氣降得慢 |

`difficulty` 只是**標籤 + 前端徽章**用;真正影響數值的是 `initial_anger`、`max_turns`,
以及 persona 文字。難度高 = 起點高、回合少、脾氣硬。

### 怒氣衰減係數 —— 讓「困難」真的更難【✅ 已採用 2026-06-09】
目前安撫效果全由 LLM 決定。加一個係數讓難度「機制化」、不只靠提示詞:

- 新欄位 `calm_resistance`(預設 1.0;easy 0.9、normal 1.0、hard 1.4)。
- 在 `graph/nodes.py:apply_state` 對**負向 delta**(玩家安撫成功)乘上 `1/calm_resistance`,
  讓困難關「同樣一句好話,降的怒氣比較少」。正向 delta(惹怒)**不打折**(被惹一樣痛)。
- 夾限仍在 `[-30, 30]`、血條 `[0,100]`,只是縮放安撫效果。
- 一行改動,可量化、可在報告解釋,期末展示講得出「難度怎麼實作」。

## 6. 多客人「班次」模式(shift)【新增,設計中】

> 需求:一個關卡可能有**多位客人**,有好有壞(奧客居多),服務完一個換下一個。

**資料模型**:新增「班次」概念 = 一串客人的有序清單。兩種做法:
- (A)新檔型 `shifts/*.json`:`{shift_id, name, genre, customers:[scenario_id, ...]}`,
  每個 customer 仍是現有 `scenarios/*.json`(沿用現成載入/圖譜,改動最小)。**推薦**。
- (B)在 scenario JSON 內嵌客人陣列(耦合高,不利重用)。→ 不採用。

**好客人 vs 奧客**:同一份 scenario 結構,差別只在數值/persona:
- 好客人:`initial_anger` 低(10–25)、persona 友善、`opening_line` 客氣,
  通常一兩句就 `happy`;偶爾穿插當「喘息回合」。比例約 **奧客 3 : 好客 1**。
- 標記欄位 `customer_kind`:`okeke` / `nice`(前端可顯示不同底色/標籤)。

**流程(前端編排,後端幾乎不動)**:
1. 進班次 → 依序 `POST /api/start` 第一位客人(各客人 = 各自 graph thread)。
2. 一位結束(success/fail/timeout)→ 顯示**該客小結**→ 自動換下一位。
3. 全部跑完 → **班次總報告**:平均分、總成本、滿意客數/客訴數、連續和解 streak。
4. (optional)後端加 `GET /api/shifts`、`/api/shift/{id}` 只是回客人清單;
   評分/對局仍走現有 `/api/say`。

**最小改動**:新增 `shifts/` + loader 的 `list_shifts()`;前端 select 畫面多一層
「選班次 → 班次內依序」。單客人模式仍可保留(相容)。

> 【✅ 已實作 2026-06-09】採「前端編排、後端不動」:選關畫面改難度色階(藍簡/粉中/綠難,藍寬→綠窄),
> 點任一難度關卡 = 進入該難度班次,依序服務同難度多位客人 → 班次總報告(平均分/滿意客訴逾時數/連續和解/總成本)。
> 聊天紀錄改「每位客人折疊區」避免過長。新增 2 個 nice 好客當喘息。共 8 關(easy3/normal3/hard2)。
> 待補:依「越難越多奧客」再加困難關;nice 客人和解門檻偏高可再調語氣;歷史可改存班次層級。

## 7. 成本預算機制 —— 修「照單全收就滿分」【新增,重要】

> 痛點實測:只要照奧客要求做(給折扣/免單/送東西),很容易滿分。
> 要讓「在**一定成本以內**讓客人開心」才是高分。

**核心**:每次「讓步」都有**成本**,給一個**預算上限**,滿意度要在預算內達成。

**做法(LLM 估成本,改動小、契合自由對話)**:
1. scenario 加 `cost_budget`(如 100;代表可動用的讓步額度/原則彈性)。
2. **奧客回合 schema 增欄位 `concession_cost`(0–N)**:LLM 評估「店員這句話讓掉多少」——
   - 純同理、給資訊、設限、提替代方案 → 0。
   - 小讓步(送小東西/打小折)→ 10–30;大讓步(免單/退一賠十/破例)→ 40–100。
3. 後端累積到 state `cost_spent`(`Annotated[..., operator.add]` 或單值累加)。
4. **評分接成本**:
   - 報告新增第 4 維 **「成本控制 Cost-control」**:`cost_spent <= budget` 給高分,
     超支線性扣分(`max(0, 100 - (cost_spent-budget)*k)`)。
   - 綜合分改為 4 維平均(同理/危機/法規/成本控制),**無原則讓步=成本爆表=綜合分被拉下來**。
   - JUDGE prompt 明令:**「拿公司資源換和平、無條件答應不合理要求」要重扣**,
     獎勵「用同理 + 設限 + 替代方案在低成本下化解」。
5. 前端:meter 區加一條**「讓步成本 cost_spent / budget」**小條(本關色),即時可見;
   成本爆表時變紅,提醒玩家「你在花錢買和平」。
6. (選用更游戲化的 B 案)做「處理手段選單」按鈕,每顆已知成本 → 之後再考慮,先走 A。

**結局互動**:就算 `success`(奧客滿意),若 `cost_spent > budget` → 報告標「和解但超支」、
綜合分顯著下降;反之低成本和解 = 真高手。可加成就「零成本和解」。

## 8. 髒話 / 語氣尺度 —— `swear_level`【新增】

期末展示場合,要真實但不過火。persona 加欄位 `swear_level`:

| level | 用語 | 適用 |
|------|------|------|
| 0 溫和 | 客氣but固執、不罵人 | 好客人、簡單關 |
| 1 帶刺 | 嗆、酸、沒禮貌(「什麼爛服務」「聽不懂?」) | 普通關 |
| 2 火爆 | 情緒粗口(「靠」「搞屁」)、拍桌、嗆告 | 困難關 |

- **允許**:情緒性粗口、嗆聲、威脅投訴/PO 網。
- **禁止**:重度髒話(問候家人)、性/下流、歧視(性別/地域/種族)、霸凌式人身攻擊。
- 在 `prompts/customer_system.txt` 依 `swear_level` 給語氣指引;預設 1。

- 加關卡記得 `ending_lines` 三種都要寫,否則 `_validate_scenario` 會擋下。
- 成本機制靠 LLM 估 `concession_cost`,可能有抖動 → 後端夾限 + 重試;展示前校準幾局。
- `avatar` 欄位目前指向 `assets/*.png`(Gradio 用);web 前端走 emoji,角色圖到位再換。
- 多客人模式前端編排為主,後端盡量不動現有 `/api/say`,降低回歸風險。
- 新增欄位(`calm_resistance`/`cost_budget`/`swear_level`/`customer_kind`)一律**給預設值**,舊關卡不報錯。
